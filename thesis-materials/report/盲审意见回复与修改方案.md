## M2：性能评估仅使用单一测试场景

### 回复

感谢审稿人对实验覆盖面的关注。我们对此问题进行如下澄清和回应：

**（1）端到端加速比中，场景复杂度仅影响 $T_B$（GPU 查询阶段），不影响 $T_A$（CPU 状态推进阶段）。** Wavefront 主循环的 CPU 侧工作（merged\_pass: advance / collect / distribute / harvest + compact + refill）逐路径遍历路径池数组，执行状态机转移和请求/结果的读写，其耗时由路径池容量和 `path_state` 结构体的 Cache 访问模式决定，与场景的三角面片数量无关。当场景规模从 13K 增长至百万面片时，BVH 深度增加导致 $T_B$ 增长，但 $T_A$ 保持不变。

**（2）场景规模增大对本方法有利，而非不利。** 在当前实验配置下 $T_A \gg T_B$（即 CPU 侧是瓶颈），$T_B$ 的增长实际上使 $T_A / T_B$ 比值趋近 1，即进入 Ping-Pong 延迟隐藏效率最高的工作区间。理论上，端到端加速比 $S_{\text{e2e}}$ 可表示为：

$$S_{\text{e2e}} = \frac{T_A^{\text{baseline}} + T_B^{\text{baseline}}}{T_A^{\text{ours}} + \max(T_A^{\text{ours}}, T_B^{\text{ours}})}$$

当场景规模增大使 $T_B^{\text{baseline}}$ 显著增长时（CPU Embree 的 BVH 遍历受 SIMD 宽度限制，其性能随 BVH 深度退化显著快于 RT Core 硬件加速），分子增长快于分母，$S_{\text{e2e}}$ 单调增长。这一分析表明 **porous 场景（13K 面片）实际上是对本方法最不利的测试条件——GPU 优势尚未充分发挥，而 CPU 侧 Cache 代价已完全暴露。**

**（3）不同场景规模的后端吞吐数据已在第四章报告。** 第四章 §4.4 以独立的 benchmark 实验报告了三类查询在不同批次规模下的 GPU 吞吐量，构成了后端能力的定量基线。端到端性能受限于单一场景确实是本文的实验局限性，其根本原因在于耦合热输运仿真的测试场景需要完整的物理配置文件（材质参数、边界条件、腔体归属、对流系数等），这些配置无法自动生成，均须手工标注。本文 13 个一致性验证场景已覆盖全部物理模块，但构造更大规模的工程场景超出了论文时间范围。

**（4）修改计划。** 将在 §3.4.5（架构意义）中增加一段理论分析，推导端到端加速比随 $T_B / T_A$ 比值的增长趋势，并明确指出 porous 场景是对本方法最不利的测试条件，更大规模场景下 GPU 优势预计更为显著。同时在 §3.4.1 实验设置中声明单场景实验的局限性及原因。

## M3：缺少关键消融实验（Ablation Study）

### 回复

感谢审稿人对实验方法学的严格要求。逐条回应如下：

**（a）CPU Wavefront + Embree 实验。** 我们认可此配置在消融实验设计中的方法论价值——它可以隔离 Wavefront 架构改造引入的 Cache 代价，与递归 Baseline 对比后形成"递归 + Embree → CPU WF + Embree → CPU WF + OptiX"的三点证据链，使各因素的独立贡献清晰可分。

该实验在当前论文提交前受限于工程时间未能开展。Wavefront 求解器的查询后端接口（submit / sync / retrieve）在设计上是设备无关的（§3.3.3），Embree 后端与 OptiX 后端通过该接口 100% API 兼容（§4.3）。因此接入 Embree 作为 Wavefront 后端在工程上是可行的，预计需要适配查询请求/结果缓冲区的序列化格式，实现代价可控。**如盲审正式要求补充此实验，作者可在修改期限内完成。**

尽管尚未实测，现有数据已允许进行定性归因：32 线程下 Ours（WF + OptiX）= 104s，与 Baseline（递归 + Embree）= 106s 几乎持平。考虑到第四章已证明 OptiX RT 吞吐量为 Embree 的 333 倍（即 $T_B^{\text{OptiX}} \ll T_B^{\text{Embree}}$），若将 Ours 的后端替换为 Embree，$T_B$ 将大幅增长。这意味着 CPU WF + Embree 配置的端到端时间必然**显著劣于**递归 Baseline——即 Wavefront 状态持久化的 Cache 代价在全线程配置下是实质性的。这一推断恰好支持本文的核心论点：Wavefront 架构的真正收益不在于 CPU 侧实例化本身，而在于它所建立的批量接口使 GPU 后端的吞吐优势得以引入，从而在整体上弥补 Cache 代价并实现微弱超越（1.02×）。**该实验如能补充，将使这一论点从定性推断升级为定量实证。**

**（b）Ping-Pong 双池 vs. 单池。** 该对比可以补充。单池模式通过在代码中禁用 View 切换即可实现，无额外工程开发量，仅需运行实验并收集数据。

**（c）SoA vs. AoS 布局。** 本文选择 AoS 布局而非 SoA 是有意的工程决策。`path_state` 结构体约 3–4 KB，包含 59 个 FSM 状态对应的异构数据字段——SoA 布局将其拆分为数十个独立字段数组，merged\_pass 遍历时每条路径的状态推进需跳跃访问多个非连续数组地址，指针间接寻址反而破坏了 AoS 下单次缓存行加载即可覆盖单条路径全部热字段的顺序访存模式。在 CPU 侧（而非 GPU 侧）执行状态推进的前提下，AoS + merged\_pass 是更优的布局选择。SoA 布局真正发挥优势的场景是 GPU 端状态推进——大量线程同时访问同一字段的不同路径实例，合并访存（coalesced access）可显著提升带宽利用率。这进一步印证了全 GPU 架构才是消除 Cache 瓶颈的根本路线。因此，在 CPU 侧 SoA 实验不具有指导意义，不作为修改内容。论文中将增加上述分析作为 SoA 不适用于 CPU 侧实例化的理由说明。

**（d）Pool size 连续扫描。** 该实验可以补充。通过将 pool\_size 参数从 1024 扫描至 32768（按 2 的幂次），收集端到端墙钟时间，即可建立 pool size 与性能的完整关系曲线，直观展现 Cache Cliff 效应的临界点。

## M4：Cache 瓶颈作为"核心架构权衡"的论述不完整

### 回复

本问题的核心与 M1 同源——均指向 CPU 侧实例化的性能天花板。统一回复如下：

**（1）关于 Cache 瓶颈的归因。** 论文当前将 Cache 压力描述为"本方法的核心架构权衡"，这一表述确实不够精确。更准确的归因是：Cache 压力是 **CPU 侧实例化**的固有约束，而非 Wavefront 架构本身的缺陷。Wavefront 等价变换将路径状态从调用栈提取为持久化结构体——该持久化是批量化的必要前提，但持久化后的存储位置不受架构约束。在 CPU 侧，工作集受限于 LLC 容量（36 MB）；在 GPU 侧，路径状态常驻显存（RTX 4090: 24 GB），工作集约束放宽近三个数量级，上述瓶颈将从根本上消除。修改后的论文将在 §3.4.4 明确区分"架构层面的设计选择"（持久化本身）与"实例化层面的实现约束"（CPU LLC 容量）。

**（2）关于未实施优化的回应。** 论文提出的 SoA 布局和冷热字段分离两个方向均面向 CPU 侧实现的增量优化。如 M3(c) 所述，SoA 在 CPU 侧 merged\_pass 场景下并非最优选择；冷热字段分离（将 `path_sfn_data` 从主结构体分离）可在一定程度上缩小活跃工作集，但不改变 $O(N)$ 遍历的带宽需求。两者均属于"在错误的计算设备上做微调"——当 $T_A \gg T_B$ 且 $T_A$ 受 LLC 容量硬约束时，CPU 侧优化的收益空间有限。本文的判断是：**面向 CPU 侧的深度优化投入产出比低于直接推进全 GPU 架构**，因此选择将有限的工程资源集中于正确性验证和瓶颈定位——这两项成果对全 GPU 架构的后续实现有直接复用价值。

**（3）关于"混合架构 vs. 全 GPU 架构"的技术路线讨论。** 将在 §3.4.5（架构意义）末尾增加一段正面讨论：分析全 GPU 方案的技术可行性（persistent thread + OptiX inline tracing / optixTraverse）、主要挑战（GPU 端复杂分支调度的 warp divergence、动态内存管理）以及本文 CPU 侧实例化成果（FSM 设计、状态字段定义、接口协议）对全 GPU 实现的直接复用性。

**（4）$T_A / T_B$ 时间分解。** 同 M1(4)，将补充实测数据。

## N2：对流模型退化为牛顿冷却定律

## N4：线性化辐射系数 $h_R$ 的有效性域

### 回复

$h_R = 4\sigma\varepsilon T_{\text{ref}}^3$ 的线性化是 Bati 等人 null-collision 框架的组成部分（其论文 §6.3）。线性化误差在 $|T - T_{\text{ref}}| / T_{\text{ref}} > 0.3$ 时显著，导致 null-collision 接受率下降、方差增大——这正是 PicardN 递归子路径存在的原因：通过多轮子路径采样迭代收紧 $T_{\text{ref}}$ 的估计，使 $h_R$ 的线性化近似趋于有效。验证实验 E5 的温度范围（-244K 至 2068K）之所以仍能通过 $3\sigma$ 检验，正是因为 PicardN 机制有效控制了线性化误差。
