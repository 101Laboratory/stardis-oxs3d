## 逐条响应

### 1. §3.2.4 路径状态字段集合——与挂起点的映射关系不充分

**审计意见**: 本节仅列出字段类别，但未与表 3.1 中的具体挂起点建立明确映射关系，论证严密性不足。建议以 1-2 类字段为例说明其如何对应特定挂起点的恢复需求。

**响应**: 接受。当前 §3.2.4 确实只做了类别级枚举（五类字段），但缺少从字段到具体挂起点的反向追溯示例。

**整改方案**:
在 §3.2.4 五类字段枚举之后，增补一段以"过程局部变量联合体"和"几何与传播状态"为例的映射论证，具体说明：
- **几何与传播状态**（当前位置、传播方向、当前腔体编号）→ 覆盖全部 19 个挂起点（任何恢复均需知道路径当前几何位置）；
- **过程局部变量联合体** → 以 BND-SF 的 `reinject_sample` 和 WoS-CND 的 `wos_step` 为例: BND-SF 挂起点恢复后需读取 δ 偏移候选射线命中结果以决定界面类型，对应字段 `bnd_sf_reinject_hit`；WoS-CND 挂起点恢复后需读取当前球面半径 `r_sphere` 以计算下一步步长，对应字段 `wos_local.r_sphere`。
- 结论句：每个字段至少被一个挂起点的恢复逻辑引用，无冗余；每个挂起点的恢复逻辑所需变量均已被某字段覆盖，无遗漏。

**改动位置**: [3_ParallelizedSolver.tex](Chapters/3_ParallelizedSolver.tex#L142-L148)，§3.2.4 "路径状态的最小必要字段集合"段落末尾增补。

### 2. §3.4.2.1 验证场景——13 场景只详述 5 个

**审计意见**: 提及"13 个验证场景"，但正文只详细描述 5 个（A2, A3, D1, E3, E5），其余 8 个以"辅助测试"一笔带过。缺乏对"阶梯"构成的说明，削弱验证系统性。

**响应**: 接受。当前对 8 个辅助测试的描述确实过于简略。

**整改方案**:
在"统计汇总"段落（表 3.4 前方），增补一段文字说明 13 个验证场景的**物理复杂度递进阶梯**设计。具体方式：
- 将 13 个场景按物理复杂度分为 4 个阶梯层级：
  - **Layer 1 — 单模态稳态**（纯传导）：A2（体积热源）、A3（接触热阻）、A7（内嵌透明体）
  - **Layer 2 — 多模态稳态**（传导+辐射/对流）：B3（边界通量剖面）、B5（三线性场）、C3（Picard 导热-辐射耦合）、F1（太阳外部通量）、F2（漫射辐照）
  - **Layer 3 — 瞬态**（时间积分）：D1（对流指数衰减）、D2（非均匀对流）、E3（扩散方程精确解）
  - **Layer 4 — 多域耦合瞬态**（全耦合）：E5（流体-固体-大气）、I1（嵌套体积功率）
- 说明前 5 个详述场景选取原则：每层至少选 1 个代表，优先选择有**封闭解析解**的场景
- 8 个辅助场景的作用：在同阶梯层级内覆盖正交物理参数变体

**改动位置**: [3_ParallelizedSolver.tex](Chapters/3_ParallelizedSolver.tex#L715) 一致性验证节，在表 3.4 前（"统计汇总"段落开头处）插入说明文字。

### 3. §3.4.3.3 Cache 压力——辩护性过强

**审计意见**: 将"Cache 压力"定位为"核心架构权衡"而非待优化问题，可能削弱论文在"性能提升"方面的贡献。建议调整表述，承认瓶颈客观存在的同时强调 Wavefront 为利用 GPU 批量吞吐所必须，并将 Cache 压力转化为工作展望的引子。

**响应**: 部分接受。Cache 压力确实是 Wavefront 持久化设计的固有代价（此判断不变），但当前行文的辩护语气（"不应被简单解读为'加速比不佳'的负面结论"）可适度弱化。

**整改方案**:
- 保留"Cache压力是持久化路径状态以实现批量化的固有代价"的核心论点
- 删除/弱化"不应被简单解读"的辩护性开头，改为客观陈述
- 增补 1-2 句将 Cache 压力明确连接到工作展望：点出 SoA 布局、冷热字段分离已在 §3.4.3.2 中分析、属于**已识别的明确优化方向**，且第六章展望中将进一步讨论
- 整体基调: "当前 Cache 压力是 CPU 侧持久化的必然代价 → 已精准定位瓶颈并给出可行优化路线 → 本章贡献在于完成架构改造并严格验证等价性，为后续优化奠定基础"

**改动位置**: [3_ParallelizedSolver.tex](Chapters/3_ParallelizedSolver.tex#L966-L980) "架构意义"小节。

**具体改写草案**:

原文:
> 上述性能数据不应被简单解读为"加速比不佳"的负面结论。从三个层面来看，实验结果具有明确的科学价值：

改为:
> 端到端实验结果在验证架构正确性之外，同时揭示了当前混合架构的性能特征与优化空间：

原文（第3点结尾后）增补:

### 4. §4.1 引言——措辞过于绝对

**审计意见**: "本章的起点正是这两个结论的交汇处：批量查询请求已具备，其GPU 高效执行所需的映射方案尚未确定"表述稍显绝对。第三章已实现 Wavefront 架构并提及使用 GPU 后端，第四章更像是深入阐述和优化 GPU 后端实现方案。

**响应**: 接受。第三章的 Wavefront 实现确实已包含 OptiX 后端的初步使用，第四章是对该后端的**独立、深入设计阐述**。

**整改方案**:
将原句改写为:

> 第三章的 Wavefront 架构将全部几何查询从逐路径同步提交改造为按批次统一提交，每轮积累的同类请求量达数十万条。本章旨在为这些批量请求设计高效的 GPU 执行方案——针对三类查询（RT、CP、ENC）中的非平凡映射问题（CP 的语义重构、ENC 的拓扑论证），给出基于 NVIDIA OptiX 的统一后端管线设计，并通过定量实验验证映射方案的有效性。

**改动位置**: [4_RTBackend.tex](Chapters/4_RTBackend.tex#L6) §4.1 引言第一段，替换"本章的起点正是这两个结论的交汇处……尚未确定。"一句。

**整改方案**:
按以下结构撰写第六章（约 2000 字）：

#### 6.1 总结（~1200 字）

**第一段 — 研究问题回顾**（~200 字）:
- 重述研究问题：基于路径追踪的蒙特卡洛耦合热输运红外仿真，计算量大，现有 CPU DFS 架构无法利用 GPU 并行加速
- 本文目标：设计 CPU-GPU 混合架构实现全链路加速

**第二段 — 贡献 1: Wavefront 求解器（第三章）**（~300 字）:
- DFS→FSM 等价变换方法，19 个挂起点、三类查询、五类字段的完整规约
- Wavefront 批处理执行模型 + CPU-GPU 混合架构 + 双流 Ping-Pong 延迟隐藏

- 端到端统计等价性: 153,976 有效像素零显著差异
- 性能: 8~16 线程下 1.3~1.4× 加速，瓶颈精准定位于 CPU Cache Miss

**第三段 — 贡献 2: OptiX 光追后端（第四章）**（~300 字）:
- 三类查询的 GPU 映射方案：RT（原生映射）、CP（语义重构为射线查询）、ENC（拓扑分解为 CP+射线）
- 统一 OptiX Pipeline 架构，五套 SBT 路由
- 吞吐性能: RT 查询 5.15 GRays/s（vs Embree 15.45 MRays/s，~333× 加速）
- 引用第四章各查询类型的具体加速比数据

**第四段 — 贡献 3: GUI 编辑器（第五章）**（~200 字）:
- 五类使用痛点→八项功能需求→五大功能模块
- 场景文件解析/编辑、3D 可视化、画笔标注、任务队列调度
- 降低使用门槛，形成完整仿真工作流

**第五段 — 关键结论**（~200 字）:
- 三大贡献共同构成从算法内核到用户工具的完整技术链
- Wavefront+OptiX 混合架构的物理等价性得到严格验证
- GPU 硬件光追的批量查询加速在耦合热输运领域首次实现端到端集成

#### 6.2 工作展望（~800 字）

**第一段 — 当前局限性**（~300 字）:
- CPU 侧 Cache 压力（§3.4.3.2 分析，Pool 16K → 2.25× 退化）
- 验证场景有限性（目前 13 个验证场景，偏中小规模）
- 编辑器功能范围（无材质库、无动画时间线）

**第二段 — 方向 A: 全 GPU 求解器**（~150 字）:

**第三段 — 方向 B: 多 GPU / 大规模场景**（~100 字）:

**第五段 — 方向 D: 实时化与编辑器增强**（~150 字）:
