## 一、论文概要与总体印象

本文围绕蒙特卡洛耦合热输运红外仿真的 GPU 加速问题，提出三项贡献：(1) 将递归路径追踪求解器等价变换为基于有限状态机的 Wavefront 批处理架构；(2) 基于 NVIDIA OptiX 设计统一 GPU 查询后端，将 RT/CP/ENC 三类异构几何查询映射至 GPU 硬件光追管线；(3) 设计 GUI 场景编辑器 StardisEditor。

论文在算法等价变换的理论论证和物理一致性验证方面体现了扎实的工作量，FSM 状态机设计（59 个状态、19 个挂起点）具有较高的工程复杂度，实验设计中的统计检验方法（逐像素 Z 检验 + 多重比较校正）在同类工作中较为罕见。然而，端到端性能结果不尽理想（32 线程仅 1.02× 均势，最佳加速比仅 1.37×），且性能评估仅依托单一测试场景，削弱了结论的说服力。以下从五个维度展开详细评审。

## 三、重大研究漏洞与逻辑问题

### 漏洞 1: 端到端加速效果与研究目标的根本矛盾

论文题目为"混合架构耦合热输运…红外仿真算法"，研究动机是"突破递归求解器的计算效率瓶颈"（§1.1）。然而实验结果显示：
- 32 线程：加速比 1.02×（无加速）
- 16 线程：加速比 1.34×
- 8 线程：加速比 1.37×
- WF+Embree（无 GPU）：**4.0× 退化**

这组数据的逻辑含义是：**Wavefront 架构本身引入了巨大的性能退化（4×），GPU 后端仅将其弥补回基线水平。** 换言之，本文的两项核心贡献（Wavefront + GPU 后端）的联合效果是"回到原点"，而非突破效率瓶颈。

论文在 §3.4.3.6-§3.4.3.8 对此做了诚实的归因分析（CPU Cache miss），并在第六章指出全 GPU 才是根本解决方案。但问题在于：**论文未实现全 GPU 方案，当前 CPU-GPU 混合方案本身未能实现"突破效率瓶颈"的研究目标。** 论文的实际定位应更准确地表述为"为全 GPU 演进提供架构验证与性能基线"，而非"实现 GPU 加速"。

**建议**: 在摘要和结论中明确区分"架构验证"（已完成）和"性能突破"（未完成），避免给读者造成"已实现显著加速"的误导。当前摘要中"两项贡献协同下…达到性能均势"的表述是诚实的，但"性能均势"本质上意味着未实现加速，应在行文中更明确地承认这一事实。

### 漏洞 2: 单场景性能评估的普适性问题

全部端到端性能数据来自 porous 场景（13,010 面片）。论文在 §3.4.3.7 试图通过公式 (3.9) 的理论推导论证"更大场景下 GPU 优势更显著"，但存在以下逻辑漏洞：

(a) 公式 (3.9) 假设 $T_A$ 不随场景规模变化。但 $T_A$ 中的 merged_pass 包含 FSM 状态转移逻辑，其中 BND 模块的分支概率（$P_\text{cond}$、$P_\text{conv}$、$P_\text{rad}$）依赖于场景物理参数，不同场景的路径平均长度和状态转移模式可能不同，影响 $T_A$。

(b) 论文称"耦合热输运仿真的测试场景需要完整的物理配置文件…均须手工标注"作为单场景的理由。但 13 个一致性验证场景已经具备完整物理配置，虽然部分过于简单，但至少可以选择其中 2-3 个较复杂的场景（如 E5 多域耦合瞬态）报告端到端性能时间，以提供多场景下的性能趋势数据。

**建议**: 至少补充 2-3 个一致性验证场景的端到端墙钟时间与加速比数据，即使这些场景规模较小也比仅有一个场景的数据更有说服力。

### 漏洞 3: 333× RT 吞吐量优势的实际意义

第四章报告 GPU RT 查询吞吐量为 CPU Embree 的 333 倍，这一数字在论文摘要、引言和结论中被反复引用。但这一指标在端到端性能中几乎没有实际意义：
- $T_B^{\text{dev}}$ 仅占墙钟时间的 10.9%
- 即使 $T_B^{\text{dev}} \to 0$，端到端加速上界仅 1.12×

333× 的吞吐量优势完全被 CPU 侧状态管理瓶颈（$T_A$）所稀释。论文虽在 §3.4.3.2 做了这一分析，但在后续行文（第四章小结、第六章总结、摘要）中仍将 333× 作为核心成果指标突出呈现，存在论述重点倾斜之嫌。

**建议**: 将 333× 定位为"查询子系统的微基准测试结果"，而非端到端系统的性能指标。在摘要和结论中，应优先强调端到端加速比（1.02×-1.37×），333× 作为补充参考。
