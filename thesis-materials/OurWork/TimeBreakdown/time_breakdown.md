## 1. 定义

| 符号 | 定义 | 组成阶段 |
|------|------|----------|
| $T_A$ | CPU 状态推进耗时 | `merged_pass` + `compact+rfill` + `housekeeping` |
| $T_B^{\text{dev}}$ | GPU 设备侧查询耗时 | `gpu_kernel` + `d2h_wait` + `submit_launch` |
| $T_B^{\text{host}}$ | CPU 侧查询后处理耗时 | `trace_post`（含 cpu_postprocess） |
| $T_B$ | 总查询管线耗时 | $T_B^{\text{dev}} + T_B^{\text{host}}$ |

**物理含义**:
- $T_A$ 对应 Ping-Pong 管线中的 CPU 状态机遍历 + 路径压缩 + 管理开销
- $T_B^{\text{dev}}$ 对应 GPU 上 OptiX kernel 执行 + Device→Host 结果传输 + kernel launch 开销
- $T_B^{\text{host}}$ 对应 CPU 对传输回的查询结果的后处理
- 在双池模式下，$T_A$ 与 $T_B^{\text{dev}}$ 可通过 Ping-Pong 机制重叠执行

## 3. 关键发现

### 3.1 CPU 状态推进为主瓶颈

所有双池配置下 $T_A \gg T_B^{\text{dev}}$（5.1×–18.4×），GPU 查询管线设备侧耗时始终被 CPU 侧完全覆盖。

- **小池**（1024–4096）：$T_A / T_B^{\text{dev}} \approx 5$–$6\times$，瓶颈在频繁 compact+refill 导致的 merged\_pass 绝对时间大
- **大池**（16384–32768）：$T_A / T_B^{\text{dev}} \approx 15$–$18\times$，pool 过大导致 merged\_pass 退化（遍历大量已终止路径），$T_B^{\text{dev}}$ 反而因批量效率提高而减小
- **最优池**（8192）：$T_A / T_B^{\text{dev}} = 6.5\times$，$T_A$ 最小（77.0s），Wall 最短（108.6s）

### 3.2 单池 vs 双池对比（pool=8192）

| 指标 | 单池 | 双池 | 变化 |
|------|-----:|-----:|-----:|
| $T_A$ | 64.2s | 77.0s | +20%（双池多了池切换开销） |
| $T_B^{\text{dev}}$ | 63.8s | 11.8s | −81%（双池 Ping-Pong 隐藏 GPU 等待） |
| $T_B^{\text{host}}$ | 13.6s | 17.5s | +29% |
| Wall | 169.2s | 108.6s | −36% |
| coverage | 99.9% | 120.3% | +20pp |

**单池 $T_A \approx T_B^{\text{dev}}$（1.0×）** → CPU/GPU 串行执行，无重叠。  
**双池 $T_A/T_B^{\text{dev}} = 6.5\times$** → GPU 完全被隐藏在 CPU 推进期间。

### 3.3 D2H 传输隐藏率

| Pool | D2H Hidden% | 含义 |
|-----:|:-----------:|------|
| 1024 | 2% | 几乎无隐藏，submit 后立即 stall 等待 D2H |
| 2048 | 9% | 略有改善 |
| 4096 | 20% | |
| 8192 | 35% | 最优 wall time 点 |
| 16384 | 75% | 大部分 D2H 被隐藏 |
| 32768 | 76% | 大部分 D2H 被隐藏 |
| 8192 (single) | 52% | 单池内 async 机制也有部分隐藏 |

> D2H hidden% 随 pool 增大单调递增：批量越大 → kernel 执行时间越长 → CPU 有更多时间在 kernel 结束之前完成上一批后处理。

### 3.4 $T_B^{\text{host}}$（trace\_post）不可忽略

`trace_post`（CPU 对查询结果的后处理）在小池配置下是 $T_B$ 的主要成分：
- pool=1024：$T_B^{\text{host}} = 101.6\text{s}$，占 $T_B$ 总量的 69%
- pool=8192（双池）：$T_B^{\text{host}} = 17.5\text{s}$，占 $T_B$ 总量的 60%

该部分无法被 Ping-Pong 隐藏（必须在本次 view 内完成），是下一步优化的重点方向。
