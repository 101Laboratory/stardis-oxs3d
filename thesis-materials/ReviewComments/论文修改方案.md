## 三、逐项修改方案

### 3.1 第六章 6.2 节"全 GPU 求解器架构"细化（对应 P1-1、P2-4）

**目标位置**：[Chapters/6_Conclusion.tex](Chapters/6_Conclusion.tex) 第 6.2 节"（一）全 GPU 求解器架构"段落。

**当前问题与定位修正**：现版段落沿用了较早版本的工作描述，存在两点偏差需要在终版中修正：
1. PicardN 递归栈（\texttt{path\_sfn\_data}）实际上**已经**从 \texttt{path\_state} 分离为独立的 SoA 数组（\texttt{pool->sfn\_arr[]}，约 3.7~KB/slot），并非未来工作；该字段进一步的"无栈化"（以 PENDING Pool 方式将祖先帧外化为独立路径 slot）已有具体设计草案，可作为后续明确方向之一。
2. 全 GPU 演进的根本目标是把路径状态调度迁入 GPU 显存，CPU 末级缓存不再是优化目标。涉及 "L1/L2 友好"" 缓解 LLC 压力" 等以 CPU 缓存为指向的措辞应删除——在全 GPU 路线下这些指标不再相关。
3. 真正的核心工程难点是 **GPU 端 Wavefront 调度内核的实现**：执行模型组织、状态推进与查询发起的内联融合、warp 级路径同质化、SoA 数据组织的进一步推进等。现版对这一难点只作概括描述，应作为本节重点深入讨论。

**修改方式**：将原段落改写为五个子点——"动机定位—GPU 端 Wavefront 调度内核设计—状态机内联光追融合—warp 发散与同质化—架构成果可复用性 + PicardN 栈外化方向"。

**建议增补内容（要点）**：

> （一）全 GPU 求解器架构。
>
> **动机定位**：第三章 §3.4.3 节的路径池容量退化实验（8\,192 $\to$ 16\,384，2.25×）与 $T_A/T_B$ 时间分解（GPU 设备侧仅占墙钟 10.9\%、上界加速比 1.12×）共同表明，CPU 端的路径调度（advance/cascade/distribute）已成为当前混合架构的主导约束，GPU 侧并非瓶颈。消除该约束的根本路径是将路径池与状态调度整体迁入 GPU 显存（RTX 4090: 24~GB，相较 CPU 末级缓存容量数量级放宽），并在 GPU 端原生组织 Wavefront 执行模型。
>
> **GPU 端 Wavefront 调度内核设计**：在 GPU 侧的实例化中，调度本身不再是 CPU 主控的批次循环，而是 GPU 上的持久线程（persistent thread）网格——每个 warp 持续从路径池消费 active 路径，完成"状态推进 $\to$ 查询发起 $\to$ 结果写回"全过程，避免显式 \texttt{optixLaunch} 在每轮间产生的 host 端 kernel 启动开销与跨 kernel 数据搬运。\texttt{path\_state} 在 GPU 端需进一步推进 SoA 化（当前 GPU 实例化中除已外化的 \texttt{sfn\_arr}、\texttt{enc\_arr} 等冷区外，hot 区仍按结构体 slot 组织），使 advance 阶段对热字段的访问由 lane 级分散读写转换为 warp 级合并访存。
>
> **状态机与内联光追融合**：第四章 OptiX 查询管线（RT/CP/ENC）当前以独立 \texttt{optixLaunch} + Shader Binding Table 路由的形式与求解器解耦。在全 GPU 实例化中，查询应改由 OptiX 内联接口（\texttt{optixTraverse} 与 \texttt{optixReportIntersection}）在调度 kernel 内直接发起，CP/ENC 的几何重构方案（自定义 AABB 代理、Jordan–Brouwer 分解）可作为内联函数嵌入主 kernel；这使 FSM 状态推进与查询执行融合为同一个 kernel 内的指令流，彻底消除"主机批量提交 $\to$ 设备执行 $\to$ 主机回填"的跨设备同步链。
>
> **warp 发散与路径同质化**：第三章 FSM 设计的 59 个状态在同一 warp 的 32 个 lane 内极可能高度分歧，直接执行会显著拉低 SIMT 利用率。借鉴现代高性能 Wavefront 路径追踪器（如 Falcor 体系）的成熟做法，可在每轮 advance 前以 stream compaction 按状态 ID 对 active 路径重排，使 warp 内 lane 状态同质化；进一步可对查询类型（RT/CP/ENC）做二次分桶，使 warp 内查询路径同质化以提高 RT Core 利用率。这是全 GPU 实例化中最关键且工作量最集中的工程难点。
>
> **PicardN 递归栈进一步外化**：PicardN 的祖先帧栈（\texttt{path\_sfn\_data}）在本文 GPU 实例化中已从 \texttt{path\_state} 分离为独立 SoA 数组 \texttt{sfn\_arr[]}，使热区 \texttt{path\_state} 不再承担栈帧重量；进一步的优化方向是将该栈完全外化——以 PENDING Pool 方式将祖先帧迁移为独立 path slot，通过父子 slot 关联实现状态切换，从而消除 \texttt{sfn\_arr} 整列。该方案的关键约束（RNG 可分流后端、PENDING/active 路径的 warp 利用率、嵌套链上 slot 容量、heat\_path 跨路径一致性）已在内部设计草案中识别，可作为全 GPU 路线下的后续优化项。
>
> **架构成果可复用性**：本文 CPU 实例化所完成的 FSM 设计（59 状态、转移规则、三类查询挂起点标注）、\texttt{path\_state} 字段与冷热分组（已落实 \texttt{sfn\_arr}/\texttt{enc\_arr}/\texttt{ext\_arr} 等冷区外化）、批量查询接口协议（RT/CP/ENC 提交-回填 ABI），在架构层面与执行设备无关，可被全 GPU 实例化直接复用。CPU 端的工程价值在于以受控对照的方式验证了 Wavefront 等价改造的正确性与 GPU 查询后端的吞吐上限，并定量定位了 CPU 调度的性能天花板，为全 GPU 演进提供了实验依据。

**实施提示**：
- **删除**所有 "L1/L2 友好""LLC 压力""压缩至 512 B"等以 CPU 缓存为优化目标的措辞——在全 GPU 路线下这些不构成目标；
- 将 PicardN 栈外化定位为"已部分完成（SoA 数组化）+ 进一步明确方向（PENDING Pool 完全外化）"，不再描述为"未来工作的内存分离"；
- SoA 表述需严谨：当前 GPU 实例化已对 \texttt{path\_state} 的若干冷区做了 SoA 外化（\texttt{sfn\_arr}/\texttt{enc\_arr}/\texttt{ext\_arr}/\texttt{scn\_arr}），未完成的是 \texttt{path\_state} 热区本身的 SoA 化；
- 凡涉及未实测数字一律使用"预计/量级/趋势"等限定语；仅引用论文中已实测的数字（10.9\%、1.12×、2.25×）；
- 不引入任何"加速 X 倍"形式的新预测数字。

#### 3.2.2 第三章性能分析末——几何敏感性定性讨论段

**目标位置**：[Chapters/3_ParallelizedSolver.tex](Chapters/3_ParallelizedSolver.tex)，§3.4.3 时间分解之后、"小结"之前。

**当前问题**：性能评估集中在 porous（约 13K 三角形），未对其他几何特征下的行为给出讨论。

**建议增补内容**（**定性**讨论，不引入新数字、不展望多 GPU 互联——多 GPU 在混合架构 GPU 非瓶颈、纯 GPU 尚未实现的当前阶段属于"越级"展望）：

> **几何特征敏感性讨论**。本文性能评估场景 porous 在单一案例中同时覆盖辐射、传导、对流三类物理过程，是验证耦合求解物理一致性的代表性场景，但其几何复杂度与腔体拓扑相对均质。基于本节 $T_A/T_B$ 时间分解模型与 BVH 遍历的渐近行为，可对其他几何特征下的性能趋势作如下**定性预期**：
>
> （1）**高面片密度薄壁结构**：BVH 深度随面片数对数增长，GPU 端单条 RT 查询的遍历开销小幅上升，但 RT Core 的硬件加速使单查询绝对耗时仍稳定在亚微秒量级；CPU 调度侧的 advance/cascade 开销与几何复杂度无关，因此整体加速比的变化预期有限。
>
> （2）**多嵌套腔体结构**：ENC 查询频次随腔体层级近似线性增长，但本文 ENC 分解为一次 CP + 一条 $+X$ 射线的实现保持了每次 ENC 仅两次 \texttt{optixLaunch} 的复杂度上界；该类场景下 GPU 后端相对 CPU 后端的吞吐优势预期会进一步显现。
>
> （3）**超大规模工业级场景**：当几何规模显著超越 porous（如百万级三角形）或路径池工作集进一步膨胀时，CPU 端调度瓶颈预期会先于 GPU 端饱和而触顶；该情境下根本解决方案不在于扩展硬件并行度，而在于将路径调度本身迁入 GPU（详见第六章展望）。
>
> 上述讨论为基于已有模型的趋势预期，不构成实测结论；系统化的多场景扩展性验证留待后续工作，本文 GUI 编辑器与任务队列已为大规模批量实验提供工具支持。

- 必须使用"定性预期""趋势""预期"等措辞，**严禁**出现"测得/达到/实验表明"等暗示新实测的表述；

#### 3.2.3 第六章 6.2 节"（二）"——改写为"借鉴现代高性能 PT 的优化技术"

**目标位置**：[Chapters/6_Conclusion.tex](Chapters/6_Conclusion.tex)，6.2 节"（二）多 GPU 与大规模场景扩展"段。

**修改决策**：**整段重写**，删除多 GPU 与 NVLink 互联展望。理由：
1. 当前混合架构中，GPU 设备侧仅占墙钟 10.9\%，**GPU 并非瓶颈**——单卡 GPU 容量未饱和，谈跨卡互联缺乏依据；
2. 纯 GPU 求解器尚未实现，多卡协作属于越级展望，在终版定稿中难以承受深入论证；
3. 现代图形界对 GPU 路径追踪有大量成熟的工程优化，**借鉴这些技术到全 GPU 求解器**是务实、可衔接、与全 GPU 路线直接对接的展望方向。

**建议改写后的段落**：

> （二）借鉴现代高性能路径追踪的工程优化技术。本文 Wavefront 求解器以耦合热输运的物理正确性为首要目标完成实例化，在调度组织、数据布局、查询同质化等工程优化维度仍保有可观的提升空间。现代图形界的高性能路径追踪器（如 NVIDIA 的 Falcor / NRD 体系、商用 DXR 渲染管线）在近年积累了一系列经实战验证的优化技术，与本文求解器结构高度同源，可在全 GPU 实例化阶段有选择地引入：
>
> （a）**Wavefront 分阶段调度**：将每轮路径推进按事件类型拆分为多个独立 kernel（生成、扩展、阴影、交互、终止等），每个 kernel 内 lane 同质性高，可显著降低 warp 发散。本文 FSM 的 59 状态天然适配此类拆分。
>
> （b）**路径排序与 Coherent Shading**：在 BSDF/材质评估阶段按材质 ID 或查询类型对路径进行 stream compaction，使同 warp 内 lane 访问相同材质资源与执行相同 shader，提升 RT Core 与 SM 利用率。
>
> （c）**SoA 路径状态与 packed 数据布局**：将 \texttt{path\_state} 在 GPU 端进一步推进为 SoA 组织，并对高频访问字段进行 bit-packed 紧凑化（如方向用八面体编码、状态用 8-bit），降低显存带宽压力。
>
> （d）**内联光追与 Shader Execution Reordering（SER）**：以 OptiX 内联接口与 NVIDIA SER 机制将查询发起与状态推进融合于同一 kernel，减少 kernel 启动与跨 kernel 数据搬运开销。
>
> （e）**自适应路径长度与 Russian Roulette**：在能量贡献低的路径段引入概率终止以降低长尾路径开销；该机制与本文蒙特卡洛框架天然兼容。
>
> 上述优化技术与本文 FSM、\texttt{path\_state}、批量查询接口设计正交，不需要对架构作根本性改动即可逐项引入；其工程化落地依赖第六章（一）所述的全 GPU 实例化基础。

### 3.3 简化假设边界与失效扩展（对应 P1-3、P2-3）

#### 3.3.1 第二章末——"建模假设与适用边界"小段

**目标位置**：[Chapters/2_Research.tex](Chapters/2_Research.tex)，"小结"之前。

**建议增补内容**：

> **建模假设与适用边界**。为聚焦于求解架构的并行化设计，本文蒙特卡洛耦合热输运框架采用以下三条工程简化假设，其在主流工业红外仿真任务中通常成立：
>
> （1）**漫射灰体表面**：表面发射率与吸收率独立于波长且与方向无关；
> （2）**透明非参与流体**：流体仅承担对流换热，不参与体积辐射散射或吸收；
> （3）**线性化对流换热系数**：对流换热在工程温区内以恒定或弱温度依赖系数近似。
>
> 上述假设的失效场景及对应的扩展路径将在第六章展望中讨论。

#### 3.3.2 第六章 6.2 节"（三）更丰富的物理模型"——按假设失效场景分级，先学术后工程

**目标位置**：[Chapters/6_Conclusion.tex](Chapters/6_Conclusion.tex)，6.2 节"（三）更丰富的物理模型"段。

**当前问题**：原稿仅从工程视角（FSM 状态数、查询管线 API 兼容性）讨论扩展性，专业性不足。各类假设失效在学术上首先意味着物理建模与统计估计层面的具体挑战——物理一致性是否仍成立、蒙特卡洛估计器是否仍无偏、概率密度分解是否仍可解析采样——这些必须先于工程实现讨论。

**改写思路**：将段落组织为"假设失效场景 $\to$ 学术层面挑战 $\to$ 工程层面扩展"三段式，每条假设失效下学术与工程并列论述。

**建议改写内容**：

> 以三条简化假设的失效场景为线索，所需的扩展同时涉及学术与工程两个层面：学术层面关注物理模型在路径空间中的可表达性、蒙特卡洛估计器的无偏性与方差可控性；工程层面关注 FSM 与查询管线的结构改动。两个层面缺一不可。
>
> **（a）参与性介质失效（烟气、火焰、薄云、气溶胶）**。
>
> *学术层面*：流体参与辐射后，路径空间从"表面—表面"扩展到"表面—体—表面"，需在路径密度中引入沿光程的指数衰减项 $\exp(-\int_0^s \sigma_t(\ell)\,\mathrm d\ell)$ 与散射相函数 $f_p$。此时蒙特卡洛估计器的无偏性要求自由飞行距离采样必须严格匹配介质消光系数（如 Woodcock null-collision 跟踪）；散射事件需通过相函数的解析或表式重要性采样保持概率密度归一；多次散射路径的方差控制依赖 Russian Roulette 与 Next-Event Estimation 等成熟方差缩减技术。本文当前耦合热输运的单路径框架在原理上与体积散射兼容（Bati 等 2023 框架已涵盖该方向），但 PicardN 在非线性辐射边界与体积参与项耦合下的收敛性与无偏性需重新分析证明。
>
> *工程层面*：在学术层面成立的前提下，FSM 需新增"介质内自由飞行—散射/吸收事件"段落（约 5\~7 个状态），GPU 查询管线需扩展 RT 类型以支持体积光线步进与采样；该类扩展属于结构性改动，但与本文 RT/CP/ENC 三类查询保持正交，不破坏现有后端 ABI。
>
> **（b）多光谱辐射失效（强温度依赖发射率、谱选择性材料、大气吸收带）**。
>
> *学术层面*：单波段灰体假设失效后，能量沿路径不再由单一频道携带，需在路径空间中引入波长维度。常见处理方式有：每条路径绑定一个波长样本并按光谱发射密度采样（Spectral Importance Sampling）、或采用 Hero Wavelength + 重要性采样的多波长协同方案。两种方案在统计上均可保持无偏，但在方差与计算成本之间的权衡不同；光谱量与温度量的耦合（如 $\varepsilon(\lambda,T)$ 与 Planck 函数 $B_\lambda(T)$ 在 PicardN 内的展开）需重新推导一致性条件。
>
> *工程层面*：在 \texttt{path\_state} 中扩展波段索引字段，材质系统由灰体单值扩展为按谱段查表，采样阶段引入波段抽样；FSM 状态拓扑与查询管线本身无需结构性改动，主要工作量集中在材质数据组织与采样模块。
>
> **（c）强非线性温差下的对流系数失效（如自然对流主导、相变换热）**。
>
> *学术层面*：线性化对流系数 $h_{cv}=\mathrm{const}$ 在 PicardN 的 null-collision 分支选择中被显式使用以保证概率归一与无偏；若 $h_{cv}=h_{cv}(T)$ 强非线性，需将其作为 PicardN 框架内的非线性项与辐射项 $h_{rd}(T)$ 同等处理，重新推导多温度采样的乘积估计形式；当 $h_{cv}$ 跨越数量级（如自然对流不同流态）时，估计器方差的可控性需通过 majorant 上界或额外的方差缩减手段保证。
>
> *工程层面*：在 advance 阶段引入温度依赖的换热系数闭包，FSM 状态机本身保持不变；属于物理模块的局部替换。
>
> **小结**。三类假设失效在学术上的挑战远大于工程上的改动：(a) 类需重新建立体积参与项与 PicardN 的耦合无偏性；(b) 类需在光谱维度上重建路径概率密度；(c) 类需扩展 PicardN 框架对非线性对流项的处理。在学术层面问题得到解决的前提下，工程层面的扩展可在本文 \texttt{path\_state} + 批量查询接口范式内逐步实施。上述扩展的理论分析、原型实现与无偏性验证留待后续工作。

#### 3.3.3 第六章 6.2 节"（四）"——改写为"仿真管线与工业/DCC 软件数据互通"

**建议改写内容**：

>
> 具体可探索的方向包括：
>
> （a）**与 CAD/CAE 工业软件的几何互通**：通过 STEP/IGES、CGNS、VTU 等中性格式或专用插件，从 CATIA、SolidWorks、ANSYS 等工业软件导入装配级几何与已划分的网格，保留装配树与材质属性映射，避免在 StardisEditor 内重复进行几何建模与材质指派。

>

### 3.4 参考文献格式统一（对应 P2-1）

**目标文件**：[ReferenceBase.bib](ReferenceBase.bib)

**修订清单**：

| # | 项目 | 操作 | 验收标准 |
|---|------|------|----------|
| 1 | 作者大小写 | 扫描所有 `author = {...}` 字段，将全大写姓名改为"首字母大写"格式（保留 BibTeX `{...}` 保护必要的姓氏大小写，如 `{van der} Berg`） | 在最终生成的 .bbl 中，作者名首字母大写、其余小写，与 GB/T 7714-2015 规范一致 |

**实施步骤建议**：

```powershell
# 1. 检索潜在大小写问题
Select-String -Path .\ReferenceBase.bib -Pattern '(?i)^\s*author\s*=' -Context 0,0

# 2. 检索页码空格问题
Select-String -Path .\ReferenceBase.bib -Pattern 'pages\s*=\s*\{[^}]*\s+--?\s+|--\s+\d|\s+--'

Select-String -Path .\ReferenceBase.bib -Pattern '\b[Vv]ol\.|VOL'

Select-String -Path .\MainBody.bbl -Pattern '^\\bibitem' | Select-Object -First 25
```

- 修改前先 `git commit` 当前 .bib 文件作为基线；
