## 2. OMP Cascade 加速效果

### 2.1 Cascade 阶段加速

| pool_size | serial (s) | OMP (s) | 加速比 |
|-----------|-----------|---------|--------|
| 4096      | 83.2      | 11.0    | **7.57x** |
| 16384     | 110.2     | 10.9    | **10.1x** |

Cascade 在两种 pool_size 下都降至 ~11s，这说明 OMP 并行化效果与 pool_size 无关——
400M 次迭代的计算量被均匀分摊给所有线程。

### 2.2 GPU Trace 意外加速

| pool_size | serial trace (s) | OMP trace (s) | 加速比 | 吞吐量提升 |
|-----------|------------------|---------------|--------|------------|
| 4096      | 150.9            | 89.6          | 1.68x  | 7.1 → 12.5 Mrays/s |
| 16384     | 128.1            | 115.5         | 1.11x  | 8.7 → 9.5 Mrays/s  |

GPU trace 本身并未修改，但也出现了加速。原因分析：

**GPU Boost 频率响应假说**：
- Serial 模式下，cascade 占用 CPU 83s，GPU 长时间空闲等待
- GPU Boost 算法在空闲期降低频率以节能
- OMP 模式下 cascade 仅 11s，GPU 空闲窗口大幅缩短
- GPU 维持在更高 Boost 频率区间 → 每次 trace 调用的实际吞吐提升
- pool=4096 效果更显著（cascade 从 83→11s，空闲窗口压缩 87%）

### 2.3 整体加速

| pool_size | serial (s) | OMP (s) | 整体加速 |
|-----------|-----------|---------|----------|
| 4096      | 287.5     | 152.7   | **1.89x** |
| 16384     | 361.9     | 239.9   | **1.51x** |

pool=4096 整体加速 1.89x，大于仅 cascade 的预期贡献
（(287.5-83.2+11.0)/287.5 ≈ 0.75 → 期望 1.33x），差异来自 GPU Boost 效应。

## 3. Pool Size 权衡分析

### 3.1 核心发现：pool=16384 比 pool=4096 更慢

这与直觉相反——更大的 pool 应该给 GPU 更多射线提高利用率？

| 指标 | pool=4096 OMP | pool=16384 OMP | 差异 |
|------|---------------|----------------|------|
| 总耗时 | 152.7s | 239.9s | **+57%** |
| compact | 5.5s | 18.7s | +240% |
| collect | 14.3s | 17.1s | +20% |
| distribute | 16.8s | 24.0s | +43% |
| harvest+refill | 8.6s | 34.5s | **+301%** |
| trace | 89.6s | 115.5s | +29% |
| cascade | 11.0s | 10.9s | ≈不变 |
| 总步数 | 123,711 | 112,222 | -9% |

### 3.2 成本模型

定义：
- $P$ = pool_size（槽位总数）
- $W$ = 有效 wavefront width（需要射线的活跃路径数）
- $A$ = active_compact（活跃路径数）

每步总成本：

$$T_{step} = \underbrace{O(P)}_{\text{compact} \times 2 + \text{update\_active}} + \underbrace{O(A)}_{\text{collect+distribute+cascade}} + \underbrace{f(W)}_{\text{GPU trace}}$$

关键观察：
- **compact 和 update_active_count 扫描全部 P 个槽位**，不论多少是活跃的
- **harvest+refill 扫 done_indices**，但 `init_single_path` 成本高昂

### 3.3 Wavefront Width W 分析

| 场景 | pool_size | avg_width W | W/P | 步数 | drain 比例 |
|------|-----------|-------------|-----|------|----------|
| 256² spp4 | 4096 | 1,970.5 | 48% | 123,711 | 11.1% |
| 256² spp4 | 16384 | 2,172.2 | 13% | 112,222 | 49.4% |
| **320² spp32** | **8192** | **6,791.2** | **83%** | **396,134** | **1.4%** |

**关键发现：W 不是绝对常数，而是场景和 pool_size 的函数。**

- 同一场景（256²）下，P 从 4096→16384，W 仅从 1970→2172（+10%）
- 换场景（320² spp32）后，W 跳至 6791——因为 3.28M 路径在 pool=8192 中
  有更高的并发度，且路径长度分布不同
- pool=8192 的 W/P=83% 表明 pool 利用率极高，drain phase 仅 1.4%

在 **同一场景** 内，W 不随 P 显著增长，因为它由 **MC 物理过程** 决定：

1. **Cascade 深度饱和**：每条路径平均需要 ~1528 次 cascade 迭代（400M iterations / 262K paths）。
   cascade 是串行推进，更多路径并不能减少每条路径的 cascade 步数。

2. **负反馈机制**：
   - 路径需要射线 → 进入 `need_ray` 集合 → 本步获得 trace → 推进
   - 路径被 cascade 推进 → 可能又需要射线 → 回到等待
   - 系统动态平衡在 W ≈ 2000（受 cascade 速度调节）

3. **对比**：pool=16384 多出的 ~12000 个槽位大多在做"空转"cascade 
   （推进后又回到需要射线），并没有增加每步的有效射线需求。

### 3.4 最优 Pool Size 估算

代入成本模型（以 OMP 基准数据校准）：

单步管理成本 $C_{mgmt}$：
$$C_{mgmt}(P=4096) = \frac{5.5 + 14.3 + 16.8 + 8.6}{123711} = 0.365 \text{ ms/step}$$

$$C_{mgmt}(P=16384) = \frac{18.7 + 17.1 + 24.0 + 34.5}{112222} = 0.840 \text{ ms/step}$$

GPU trace 单步成本：
$$C_{trace}(P=4096) = \frac{89.6 \times 10^3}{123711} = 0.724 \text{ ms/step}$$

$$C_{trace}(P=16384) = \frac{115.5 \times 10^3}{112222} = 1.029 \text{ ms/step}$$

成本最小化：P 增大 → 步数减少但单步成本上升。最优点在：
$$P^* \approx W \approx 2000\text{-}3000$$

> **建议验证**: 测试 pool_size = 2048, 2560, 3072 以确认最优点。

### 3.5 Drain Phase 影响

| 场景 | pool_size | drain 射线比例 | drain 步数 | drain wall (s) |
|------|-----------|--------------|------------|----------------|
| 256² spp4 | 4096 | 11.1% | 70,804 | 41.9 |
| 256² spp4 | 16384 | 49.4% | 104,693 | 173.9 |
| 320² spp32 | 8192 | **1.4%** | 72,195 | 63.8 |

pool=16384 的 drain phase 占总射线的 **49.4%**！
这意味着几乎一半的计算在"不满载"状态下进行——GPU 利用率极低。

相比之下，320² spp32 + pool=8192 的 drain 仅 **1.4%**，因为：
- 3.28M 路径 / 8192 pool ≈ 400 代，refill 阶段持续极久
- pool 利用率 W/P=83%，几乎所有步都在满载运行

> **启示**: drain 比例 = $\frac{P}{\text{total\_paths}}$ 的函数。当 total_paths >> P 时，
> drain 影响可忽略。

## 4. 时间分解对比

### 4.1 小规模场景（OMP 模式，pool=4096 基准）

```
trace:          89.6s  (58.7%)  ← GPU 瓶颈
collect:        14.3s   (9.4%)  ← CPU: 2-pass radix scatter
distribute:     16.8s  (11.0%)  ← CPU: bucketed dispatch
cascade:        11.0s   (7.2%)  ← CPU: OMP 并行化后已优化
harvest+refill:  8.6s   (5.6%)  ← CPU: path init
compact:         5.5s   (3.6%)  ← CPU: O(P) full scan ×2
其他/调度:       7.0s   (4.6%)  ← 未分类开销
合计:          152.7s
```

### 4.2 大规模场景（OMP 模式，pool=8192, 320² spp32）

```
trace:        1007.7s  (63.0%)  ← GPU 瓶颈
distribute:    209.8s  (13.1%)  ← CPU: bucketed dispatch
collect:       160.0s  (10.0%)  ← CPU: 2-pass radix scatter
cascade:        79.8s   (5.0%)  ← CPU: OMP 并行化
harvest+refill: 51.6s   (3.2%)  ← CPU: path init
compact:        38.7s   (2.4%)  ← CPU: O(P) full scan ×2
其他/调度:      52.4s   (3.3%)  ← 未分类开销
合计:         1600.0s
```

### 4.3 CPU 管理总成本对比

| 场景 | CPU 管理 (s) | 占比 | trace (s) | 占比 | cascade (s) | 占比 |
|------|-------------|------|----------|------|------------|------|
| 256² P=4096 | 45.2 | 29.6% | 89.6 | 58.7% | 11.0 | 7.2% |
| 320² P=8192 | 460.1 | 28.8% | 1007.7 | 63.0% | 79.8 | 5.0% |

$$T_{CPU\_mgmt}(256^2) = 14.3 + 16.8 + 8.6 + 5.5 = 45.2s \quad (29.6\%)$$

$$T_{CPU\_mgmt}(320^2) = 160.0 + 209.8 + 51.6 + 38.7 = 460.1s \quad (28.8\%)$$

**CPU 管理成本占比在两种规模下高度一致（~29%）**，说明这是结构性开销而非场景特例。

大规模场景中 collect 和 distribute **大幅增长**（14→160s, 17→210s），
因为 W 从 ~2000 增至 ~6800，每步处理射线数增加 3.4×，
而步数也增加 3.2×（124K→396K），两者乘积导致 ~11× 的累积成本增长。

## 5. 大规模场景洞察（320² spp32, pool=8192）

Take 5 验证了多项结论并提供了新的发现：

### 5.1 pool 利用率与场景规模的关系

| 指标 | 256² spp4 P=4096 | 320² spp32 P=8192 |
|------|------------------|-------------------|
| 总路径 | 262,144 | 3,276,800 |
| 路径/池大小 | 64 代 | 400 代 |
| W/P | 48% | **83%** |
| drain 射线占比 | 11.1% | **1.4%** |

当 total_paths/pool_size 的比值足够大时（≥400），pool 几乎全程满载，
drain phase 可忽略。这意味着 **对于生产级渲染任务（高分辨率、高 spp），
pool_size 的选择更宽容**——只要 P ≥ W 即可。

### 5.2 每步单位成本对比

| 阶段 | 256² 每步 (μs) | 320² 每步 (μs) | 比值 | 原因 |
|------|---------------|---------------|------|------|
| compact | 44.5 | 97.6 | 2.2× | O(P): 8192/4096 = 2× |
| collect | 115.6 | 403.9 | 3.5× | O(W): 6791/1970 = 3.4× |
| trace | 724 | 2544 | 3.5× | f(W): batch 更大 |
| distribute | 135.8 | 529.7 | 3.9× | O(W): 同上 |
| cascade | 88.9 | 201.5 | 2.3× | O(A): A 更大 |
| harvest+refill | 69.5 | 130.3 | 1.9× | O(done): 吞吐稳定 |

- compact 的增长因子 (2.2×) ≈ P 的比值 (2×)，符合 O(P) 预期
- collect/distribute 的增长因子 (3.5-3.9×) ≈ W 的比值 (3.4×)，符合 O(W) 预期
- cascade 增长 2.3× 而非 W 的 3.4×——OMP 并行效率在更大 active set 上更高

### 5.3 Cascade OMP 效率

Take 5 中 cascade 占 79.8s (5.0%)，cascade per-phase profiling 显示
各阶段累积时间远超 79.8s（因 OMP 并行，wall-clock < thread-time-sum）。

以 cascade phase[34] 为例: count=1,025,806,286 × 0.207μs/iter = 212.3s thread-time，
但 wall-clock 仅贡献 ~79.8s 的一部分。这证实了 OMP 在大 active set 上的有效加速。

## 6. 结论与后续方向

| 发现 | 影响 | 后续行动 |
|------|------|----------|
| cascade OMP 已饱和（5-7% wall time） | 无进一步优化空间 | — |
| GPU trace 占 59-63% | 是绝对瓶颈，但受硬件限制 | 考虑 kernel 优化 |
| **CPU 管理恒定占 ~29%** | **跨场景的结构性开销** | 见 [cpu_phase_analysis.md](cpu_phase_analysis.md) |
| W 由场景物理决定 | 同一场景内 W 不随 P 增长 | pool_size 应 ≈ W |
| W/P=83% 在大场景+适当P时 | 说明 pool 利用率可以很高 | 不需过大 P |
| drain phase 在 paths>>P 时可忽略 | 生产任务不受 drain 困扰 | 聚焦 refill 阶段优化 |
| collect+distribute 在大 W 下成为主要 CPU 成本 | 370s/1600s (23%) | 考虑 OMP 并行化 |

> **下一步**: 参见 [cpu_phase_analysis.md](cpu_phase_analysis.md) 了解 CPU 管理成本优化的 P0-P3 方案。
