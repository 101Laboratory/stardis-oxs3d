# CPU/GPU 时间比 ρ 对双缓冲流水线加速比的影响分析

**生成时间**: 2026-02-24  
**项目**: Stardis-GPU / stardis-cus3d  
**前置文档**: [analysis.md](analysis.md) §1–§7（双缓冲流水线可行性分析）  
**研究问题**: 在 n=2 双缓冲流水线架构下，当 CPU/GPU 时间比 ρ = T_C/T_G 发生变化时，(1) 是否存在比 50/50 更优的池分割比？(2) 加速比如何随 ρ 变化？(3) pool_size 作为 ρ 的主要驱动变量如何影响最终性能？  
**核心结论**: 50/50 分割对所有 ρ 均为（近）最优解；ρ 偏离 1 时应通过工作迁移改善比值，而非调整分割比。

---

## 1. 建模框架

### 1.1 问题定义

双缓冲流水线将 wavefront pool 分为两个 view（A 和 B），交替执行：GPU 处理 A 时 CPU 处理 B，反之。

**核心参数**：
- $N$：池总容量（pool_size）
- $p \in (0, 1)$：分割比例，view A 容纳 $pN$ 条路径，view B 容纳 $(1-p)N$ 条
- $\rho = T_C / T_G$：稳态下单个满载步的 CPU 总时间与 GPU 总时间之比

**目标**：给定 $\rho$，求最优分割比 $p^*$ 使流水线周期时间 $T_2(p)$ 最小，进而求最优加速比 $S^*(\rho)$。

### 1.2 线性缩放模型

假设每个阶段的处理时间与该 view 中的路径数成线性关系（refill 阶段保持两半均等填充）：

$$
T_G(x) = \alpha_G + \beta_G \cdot x
$$

$$
T_C(x) = \alpha_C + \beta_C \cdot x
$$

其中 $x$ 是该 view 的路径数占总池容量的比例（$x = pN/N = p$ 或 $1-p$）。

**参数含义**：
| 参数 | 含义 | 来源 |
|------|------|------|
| $\alpha_G$ | GPU 固定开销（kernel launch + upload + sync） | 实测：batch=0 时的 GPU 耗时 |
| $\beta_G$ | GPU 负载依赖项（满载时总 GPU 时间减去固定开销） | $\beta_G = G - \alpha_G$ |
| $\alpha_C$ | CPU 固定开销（compact/harvest 框架时间） | 实测：batch=0 时的 CPU 耗时 |
| $\beta_C$ | CPU 负载依赖项 | $\beta_C = C - \alpha_C$ |
| $G$ | 满载 GPU 时间：$G = T_G(1) = \alpha_G + \beta_G$ | [analysis.md §1.2] |
| $C$ | 满载 CPU 时间：$C = T_C(1) = \alpha_C + \beta_C$ | [analysis.md §1.2] |

**与 ρ 的关系**：$\rho = C / G$。

### 1.3 实测参数（pool=8192, porous 场景）

基于 [analysis.md §1.2] 实测数据：

| 参数 | 值 | 说明 |
|------|------|------|
| $G = T_G(1)$ | 1.538 ms | GPU kernel + upload |
| $C = T_C(1)$ | 1.648 ms | compact + collect + postprocess + retrace + distribute + cascade + harvest |
| $\alpha_G$ | 0.200 ms | kernel launch overhead |
| $\alpha_C$ | 0.100 ms | compact/harvest framework |
| $\beta_G$ | 1.338 ms | $G - \alpha_G$ |
| $\beta_C$ | 1.548 ms | $C - \alpha_C$ |
| $\rho$ | 1.072 | $C/G = 1.648/1.538$ |

**固定开销占比**（overhead fraction）：
$$
f_G = \frac{\alpha_G}{G} = \frac{0.200}{1.538} = 0.130 \quad (13\%)
$$
$$
f_C = \frac{\alpha_C}{C} = \frac{0.100}{1.648} = 0.061 \quad (6.1\%)
$$

### 1.4 常数模型与线性模型的关系

[analysis.md §1–§7] 使用的 **常数时间模型** 假设：无论分半与否，每半步耗时与满载步相同。即 $T_G(p) \approx G$，$T_C(p) \approx C$。

这等价于 $\alpha_G = G$，$\alpha_C = C$（纯固定开销，无线性项），在以下条件下近似成立：

1. GPU batch 足够大（>4096），kernel 启动开销占主导
2. CPU 代码分支开销与路径数弱相关

常数模型给出 $S = \frac{G + C}{\max(G, C)} = \frac{3.186}{1.648} = 1.933$。

线性模型给出更保守的估计（下文推导），差异来源于 **分半后每半步的时间小于满载步时间**。两者在 $f_G, f_C \to 1$ 时一致。

### 1.5 分析范围

- **稳态假设**：分析仅覆盖 refill 阶段（占总步数 88-97%）。refill 保持两半均等填充，两 view 路径数分别为 $pN$ 和 $(1-p)N$。
- **不考虑 drain/startup 瞬态**：drain 占 <3%（pool=8192），对全局影响可忽略。
- **n=2 固定**：不讨论 n>2（已由 §8 分析证明 n=2 最优）。
- **ρ 变化来源**：本文分析 ρ 作为参数的影响，§5 讨论 pool_size 如何驱动 ρ 变化。

## 2. 周期时间 $T_2(p)$ 的分段结构

### 2.1 流水线周期时间

双缓冲流水线将池按比例 $p$ 分割：view A 处理 $pN$ 条路径，view B 处理 $(1-p)N$ 条路径。主循环每轮执行两个 phase：

- **Phase 1**: GPU 处理 B（光追），同时 CPU 处理 A（post + between + pre）
- **Phase 2**: GPU 处理 A（光追），同时 CPU 处理 B（post + between + pre）

每轮两个 view 各推进一步，等效于串行的一步（全部 $N$ 条路径推进），周期时间：

$$
T_2(p) = \max\bigl(T_G(1{-}p),\; T_C(p)\bigr) + \max\bigl(T_G(p),\; T_C(1{-}p)\bigr)
$$

串行基线（GPU 和 CPU 顺序执行，无重叠）：

$$
T_{\text{serial}} = T_G(1) + T_C(1) = G + C
$$

加速比：

$$
S(p) = \frac{G + C}{T_2(p)}
$$

### 2.2 对称性

**命题**: $T_2(p) = T_2(1-p)$。

**证明**: 将 $T_2(p)$ 的两个 max 项交换求和顺序即得。由加法交换律：

$$
T_2(1-p) = \max(T_G(p), T_C(1-p)) + \max(T_G(1-p), T_C(p)) = T_2(p) \quad \square
$$

**推论**: $T_2(p)$ 关于 $p = 0.5$ 对称。若存在唯一最小值或最小平台区，其中心必然在 $p = 0.5$。

### 2.3 交叉点

Phase 1 交叉点 $p_1^*$: 令 $T_G(p) = T_C(1-p)$：

$$
\alpha_G + \beta_G p = \alpha_C + \beta_C(1-p) \implies p_1^* = \frac{C - \alpha_G}{\beta_G + \beta_C}
$$

Phase 2 交叉点 $p_2^*$: 令 $T_G(1-p) = T_C(p)$：

$$
\alpha_G + \beta_G(1-p) = \alpha_C + \beta_C p \implies p_2^* = \frac{G - \alpha_C}{\beta_G + \beta_C}
$$

**关键性质**: $p_1^* + p_2^* = 1$（由对称性直接得出）。

**数值验证**（pool=8192, porous 数据）：

$$
p_1^* = \frac{1.648 - 0.200}{1.338 + 1.548} = \frac{1.448}{2.886} = 0.5017
$$

$$
p_2^* = \frac{1.538 - 0.100}{2.886} = \frac{1.438}{2.886} = 0.4983
$$

### 2.4 三段结构

$p_1^*$ 与 $p_2^*$ 的大小关系决定了 $T_2(p)$ 的分段形式。

**判据**: $p_1^* > p_2^*$ 当且仅当 $C + \alpha_C > G + \alpha_G$。

定义 $\rho_{\text{sw}} = 1 + (\alpha_G - \alpha_C)/G$，则 $C + \alpha_C > G + \alpha_G \iff \rho > \rho_{\text{sw}}$。

**Case 1: $\rho > \rho_{\text{sw}}$（CPU 略重，$p_2^* < p_1^*$）：**

```
 T₂(p)
   ↑
   │ ╲                          ╱
   │   ╲                      ╱
   │     ╲____________________╱     ← 平台 = C + α_C
   │      ↑                  ↑
   │     p₂*               p₁*
   └──────┼────────┼─────────┼──→ p
                  0.5
```

| 区间 | Phase 1 瓶颈 | Phase 2 瓶颈 | $T_2(p)$ |
|------|-------------|-------------|----------|
| $p < p_2^*$ | CPU: $T_C(1-p)$ | GPU: $T_G(1-p)$ | $(G+C) - (\beta_G+\beta_C)p$ **递减** |
| $p_2^* \le p \le p_1^*$ | CPU: $T_C(1-p)$ | CPU: $T_C(p)$ | $C + \alpha_C$ **常数（平台）** |
| $p > p_1^*$ | GPU: $T_G(p)$ | CPU: $T_C(p)$ | $(G\!f_G + C\!f_C) + (\beta_G+\beta_C)p$ **递增** |

**Case 2: $\rho < \rho_{\text{sw}}$（GPU 略重，$p_1^* < p_2^*$）：**

| 区间 | Phase 1 瓶颈 | Phase 2 瓶颈 | $T_2(p)$ |
|------|-------------|-------------|----------|
| $p < p_1^*$ | CPU: $T_C(1-p)$ | GPU: $T_G(1-p)$ | $(G+C) - (\beta_G+\beta_C)p$ **递减** |
| $p_1^* \le p \le p_2^*$ | GPU: $T_G(p)$ | GPU: $T_G(1-p)$ | $G + \alpha_G$ **常数（平台）** |
| $p > p_2^*$ | GPU: $T_G(p)$ | CPU: $T_C(p)$ | $(\alpha_G + \alpha_C) + (\beta_G+\beta_C)p$ **递增** |

### 2.5 平台值的统一公式

$$
T_2^{\min} = \max(G + \alpha_G,\; C + \alpha_C)
$$

**验证**:
- Case 1 ($C + \alpha_C > G + \alpha_G$): 平台 = $C + \alpha_C = \max(G+\alpha_G, C+\alpha_C)$ ✓
- Case 2 ($G + \alpha_G > C + \alpha_C$): 平台 = $G + \alpha_G = \max(G+\alpha_G, C+\alpha_C)$ ✓

**直观解释**: 分池后，瓶颈资源（GPU 或 CPU）每轮支付两次固定开销（$2\alpha$）但只处理总量为 1 的工作（$\beta$），因此最小周期 = $2\alpha + \beta = \alpha + (\alpha + \beta) = \alpha + T(1)$。

**数值**（porous）：

$$
T_2^{\min} = \max(1.538 + 0.200,\; 1.648 + 0.100) = \max(1.738, 1.748) = 1.748\;\text{ms}
$$

### 2.6 $p = 0.5$ 始终在平台内

由 $p_1^* + p_2^* = 1$ 及两者关于 0.5 对称分布，$p = 0.5$ 始终满足 $\min(p_1^*, p_2^*) \le 0.5 \le \max(p_1^*, p_2^*)$。

因此 **50/50 分割在所有 ρ 条件下都是最优解**（或精确地说，都在最优平台区间内）。

## 3. 最优加速比 $S^*(\rho)$

### 3.1 加速比公式

由 §2.5，最优加速比（对应 $p = 0.5$ 或平台区任意点）：

$$
S^*(\rho) = \frac{G + C}{T_2^{\min}} = \frac{G + C}{\max(G + \alpha_G,\; C + \alpha_C)}
$$

定义归一化参数（以 $G$ 为单位）：
- $f = \alpha_G / G$（GPU 开销分数，$f_G = 0.130$）
- $a = \alpha_C / G$（CPU 开销相对于 GPU 总时间，$a = 0.065$）
- $\rho = C / G$

则：

$$
S^*(\rho) = \frac{1 + \rho}{\max(1 + f,\; \rho + a)}
$$

### 3.2 分段表达式

**瓶颈切换点**:

$$
\rho_{\text{sw}} = 1 + f - a = 1 + \frac{\alpha_G - \alpha_C}{G}
$$

对 porous 数据: $\rho_{\text{sw}} = 1 + 0.130 - 0.065 = 1.065$。

**$\rho < \rho_{\text{sw}}$（GPU 瓶颈）**:

$$
S^*(\rho) = \frac{1 + \rho}{1 + f}
$$

- 线性递增：$\rho$ 每增加 0.1，$S^*$ 增加约 $0.1/(1+f) \approx 0.088$
- 下界：$S^*(0) = 1/(1+f) = 0.885$（纯 GPU 工作，流水线反而更慢）
- $S^* = 1$ 的条件：$\rho = f = 0.130$（CPU 工作少于 GPU 固定开销时无收益）

**$\rho \ge \rho_{\text{sw}}$（CPU 瓶颈）**:

$$
S^*(\rho) = \frac{1 + \rho}{\rho + a}
$$

- 对 $\rho$ 求导：$\frac{dS^*}{d\rho} = \frac{a - 1}{(\rho + a)^2} < 0$（严格递减）
- 极限：$\lim_{\rho \to \infty} S^*(\rho) = 1$（CPU 完全主导，流水线逐渐失效）

**峰值**（在切换点 $\rho = \rho_{\text{sw}}$）:

$$
S^*_{\max} = \frac{1 + \rho_{\text{sw}}}{1 + f} = \frac{2 + f - a}{1 + f}
$$

数值: $S^*_{\max} = \frac{2 + 0.130 - 0.065}{1 + 0.130} = \frac{2.065}{1.130} = 1.828$

以 $G = 1.538$ ms, $\alpha_G = 0.200$ ms, $\alpha_C = 0.100$ ms 为基准：

|--------|----------|-----------|------------------|-------|------|------|
| 0.3 | 0.461 | 2.000 | 1.738 | 1.150 | GPU | 极轻 CPU |
| 0.5 | 0.769 | 2.307 | 1.738 | 1.327 | GPU | |


**特征**:
1. $\rho < f_G = 0.130$: 流水线反而更慢（$S^* < 1$），因为拆分产生的额外固定开销无法被微弱的 CPU-GPU 重叠抵消
2. $f_G < \rho < \rho_{\text{sw}}$: GPU 瓶颈区，$S^*$ 线性增长
3. $\rho = \rho_{\text{sw}} \approx 1.065$: 峰值 $S^* = 1.828$ 
4. $\rho > \rho_{\text{sw}}$: CPU 瓶颈区，$S^*$ 单调递减趋向 1.0
5. 在 $\rho \in [0.5, 3.0]$ 的实际范围内，$S^* \in [1.3, 1.8]$，双缓冲始终有效

### 3.5 与 analysis.md 估计的对比

[analysis.md §2.4] 报告加速比 1.92×，基于简化的常数时间假设（分半后每半步耗时不变）。本文使用线性缩放模型，得到 porous 场景加速比 **1.82×**。差异原因：

- 常数模型假设 $T_G(0.5) \approx G$，$T_C(0.5) \approx C$，忽略了缩放效应
- 线性模型体现了拆分导致的**固定开销加倍**代价：$T_2^{\min} = T_{\text{bottleneck}}(1) + \alpha_{\text{bottleneck}}$
- 线性模型的 1.82× 是较保守的估计；实际 GPU 呈亚线性缩放（kernel 时间对 batch size 不敏感），可能略高于此值
- 最终加速比需通过实测确认

## 4. 平台宽度 $\Delta p(\rho)$

### 4.1 公式推导

平台区间为 $[\min(p_1^*, p_2^*),\; \max(p_1^*, p_2^*)]$，宽度：

$$
\Delta p = |p_1^* - p_2^*| = \frac{|C - G + \alpha_C - \alpha_G|}{\beta_G + \beta_C}
$$

代入 $C = \rho G$，$\beta_G = G(1-f)$，$\beta_C = \rho G - \alpha_C = G(\rho - a)$：

$$
\Delta p = \frac{G|\rho - \rho_{\text{sw}}|}{G(1-f) + G(\rho - a)} = \frac{|\rho - \rho_{\text{sw}}|}{1 + \rho - f - a}
$$

### 4.2 数值表

| $\rho$ | $\|\rho - \rho_{\text{sw}}\|$ | $1+\rho-f-a$ | $\Delta p$ | 平台区间 $[p_{\text{lo}}, p_{\text{hi}}]$ | 含义 |
|--------|---------------------|-------------|-----------|-------------------|------|
| 0.5 | 0.565 | 1.305 | 0.433 | [0.284, 0.716] | 分割 28%–72% 均等效 |
| 0.8 | 0.265 | 1.605 | 0.165 | [0.418, 0.582] | |
| 1.0 | 0.065 | 1.805 | 0.036 | [0.482, 0.518] | 较窄但 0.5 在内 |
| **1.072** | **0.007** | **1.877** | **0.004** | **[0.498, 0.502]** | **极窄（porous）** |
| 1.5 | 0.435 | 2.305 | 0.189 | [0.406, 0.594] | 宽 |
| 2.0 | 0.935 | 2.805 | 0.333 | [0.333, 0.667] | 很宽 |
| 3.0 | 1.935 | 3.805 | 0.509 | [0.246, 0.754] | 几乎任意分割 |

### 4.3 物理解释

**$\rho \approx \rho_{\text{sw}}$（CPU ≈ GPU 平衡）**:
- 平台极窄（$\Delta p \approx 0.004$），意味着 50/50 附近任何微小偏离都会改变瓶颈方
- 但 50/50 仍在平台内，且平台外 $T_2$ 变化斜率 $= \beta_G + \beta_C \approx 2.9$ ms/单位 p，偏离 0.01 仅增加 0.029ms（< 2% 退化），实际影响极小

**$\rho \gg 1$ 或 $\rho \ll 1$（严重不平衡）**:
- 平台很宽（$\Delta p > 0.3$），因为弱势资源远比强势资源快，无论分割如何都不会成为瓶颈
- 但此时加速比 $S^*$ 已较低（< 1.5），分割比优化价值有限

### 4.4 结论

**分割比对性能的影响可忽略**。在所有实际 $\rho$ 值下：
- $p = 0.5$ 始终在最优平台区内
- 即使偏离平台，性能退化幅度 < 3%（偏离 0.01）
- 无需实现自适应分割比调整机制

## 5. pool_size 作为 $\rho$ 的驱动变量

### 5.1 经验观测

不同 pool_size 下的实测 CPU/GPU 时间比（数据来源: [wf_pipeline/00_overview.md], [analysis.md §1.2], [benchmark_res.md]）：

| pool_size $N$ | $T_{\text{cpu}}$ (s) | $T_{\text{gpu}}$ (s) | $\rho = T_{\text{cpu}}/T_{\text{gpu}}$ | CPU 占比 |
|------:|-------:|-------:|------:|------:|
| 4096 | 1172.7 | 1187.5 | 0.988 | 49.7% |
| 8192 | — | — | 1.072 | 51.7% |
| 10240 | 1528.5 | 1136.8 | 1.344 | 57.3% |
| 32768 | 2339.0 | 1059.5 | 2.208 | 68.8% |

### 5.2 缩放机制

**CPU 时间 $C(N)$ 的线性增长**:
- compact / collect / distribute / cascade 均遍历 $N$ 条路径 → $C(N) \propto N$
- OMP 并行的 cascade 在 4 线程下: $C_{\text{cascade}} \approx c_0 + c_1 \cdot N$

**GPU 时间 $G(N)$ 的亚线性/饱和**:
- GPU kernel 时间由内存吞吐主导（L2 crossbar bound, SOL Memory ~77%）
- 小 batch（< 500）: occupancy 不足，kernel 时间主要是启动开销
- 大 batch（> 4000）: kernel 时间趋于饱和
- 实测: batch 537 → 0.566ms, batch 8000 → 0.671ms（15× batch 仅 1.19× 时间）
- Upload/download 时间随 $N$ 线性增长，但占比较小

综合效果:

$$
\rho(N) = \frac{C(N)}{G(N)} \approx \frac{c_0 + c_1 N}{g_0 + g_1 \ln N}
$$

$\rho(N)$ 随 $N$ 近似线性增长（分母增长极慢）。

### 5.3 组合曲线 $S^*(\rho(N))$

将 §3 的 $S^*(\rho)$ 与 §5.1 的 $\rho(N)$ 组合（假设 $\alpha_G = 0.2$ ms, $\alpha_C = 0.1$ ms 对所有 $N$ 恒定）：

| $N$ | $\rho$ | $S^*(\rho)$ | $\Delta p$ | 流水线效果 |
|------:|------:|------:|------:|:---|
| 4096 | 0.988 | 1.759 | 0.043 | ✅ 优秀，接近平衡 |
| **8192** | **1.072** | **1.822** | **0.004** | ✅ **最优**（ρ 最接近 ρ_sw） |
| 10240 | 1.344 | 1.663 | 0.150 | ✅ 良好，CPU 开始偏重 |
| 32768 | 2.208 | 1.411 | 0.302 | ⚠️ 收益递减，CPU 主导 |

**最优 pool_size**: $N = 8192$ 恰好使 $\rho \approx \rho_{\text{sw}} = 1.065$，达到最高流水线加速比。

### 5.4 pool_size 的二维权衡

pool_size 选择需要同时考虑流水线加速比和 GPU batch 效率：

```
       ↑ 加速比 / GPU效率
       │
       │    GPU利用率（batch efficiency）
       │    ╱─────────────────────────────
       │   ╱
       │  ╱     S*(ρ) 流水线加速比
       │╱          ╱╲
       │         ╱    ╲
       │       ╱        ╲
       │     ╱            ╲
       └──┬────┬────┬─────┬──→ pool_size
        2K   4K   8K   16K  32K
```

| pool_size | 流水线 $S^*$ | GPU batch 效率 | 综合评价 |
|----------:|------:|:---|:---|
| 2048 | ~1.4 | 低（batch≈1000, 占用率≈15%） | ❌ GPU 严重不足 |
| 4096 | 1.76 | 中（batch≈4000, 占用率≈25%） | ✅ 良好平衡 |
| **8192** | **1.82** | 高（batch≈8000, 占用率≈27%） | ✅ **推荐** |
| 16384 | ~1.55 | 高（接近饱和） | ⚠️ 流水线退化 |
| 32768 | 1.41 | 高（已饱和） | ⚠️ CPU 主导严重 |

### 5.5 改善 $\rho$ 的正确策略

当 $\rho$ 偏离最优点（如 pool_size 较大导致 $\rho > 1.5$）时：

**正确做法 — 工作迁移**:
- 将 CPU 工作转移到 GPU（降低 $C$），使 $\rho$ 回到最优区间
- 例: Top-K filter GPU 化: $C$ 减少 0.35ms → $\rho$ 从 1.072 降至 $(1.648-0.35)/1.538 = 0.844$
- 新 $S^*(0.844)$ = $(1+0.844)/(1+0.130) = 1.632$... 但 GPU 时间也增加！需重新平衡
- 关键: 工作迁移改变 $G$ 和 $C$ 的绝对值，间接改变 $\rho$

**错误做法 — 调整分割比**:
- 改变 $p$ 无法改善性能（§4 已证明分割比在平台区内无影响）
- 极端分割（如 80/20）反而退出平台区，降低性能

**错误做法 — 增加缓冲区数量**:
- $n > 2$ 无法改善 $\rho$（[analysis.md §8] 已证明 $n = 2$ 最优）

## 6. 结论

### 6.1 核心发现

| # | 发现 | 依据 |
|---|------|------|
| 1 | **50/50 分割对所有 ρ 均为最优解** | $T_2(p)$ 对称性 + 平台区间总包含 $p=0.5$（§2.6） |
| 2 | **分割比调整对性能几乎无影响** | 偏离 0.01 的退化 < 2%；极端 ρ 下平台可达 $\Delta p > 0.3$（§4） |
| 3 | **$S^*(\rho)$ 在 $\rho_{\text{sw}} \approx 1.065$ 处达到峰值 1.83×** | GPU/CPU 开销结构决定的不动点（§3.2） |
| 4 | **pool_size 是 ρ 的主要驱动因素** | CPU $O(N)$ vs GPU 亚线性缩放使 $\rho(N)$ 单调递增（§5.2） |
| 5 | **pool_size = 8192 是当前硬件的最优工作点** | $\rho(8192) = 1.072 \approx \rho_{\text{sw}}$，同时 GPU batch 效率足够高（§5.4） |
| 6 | **ρ 偏离最优时，应通过工作迁移修正，而非改变分割比或缓冲区数量** | 分割比在平台区内无效（§4），$n>2$ 性能退化（§8） |

### 6.2 实践建议

1. **实现时固定 $p = 0.5$**，不需要分割比参数化或运行时调整
2. **保持 pool_size = 8192**（当前甜蜜点），不建议为流水线优化而改变 pool_size
3. **Top-K filter GPU 化 是提升 S* 的正确路径**：通过减少 $C$ 使 $\rho$ 更接近 1.0，可进一步提升加速比
4. **使用 $\rho$ 作为流水线健康度监控指标**：实测 $\rho$ 值即可查表估算预期加速比

### 6.3 模型局限性

- **线性缩放假设**: GPU kernel 实际呈亚线性缩放（batch 8000 vs 4000 时间差 < 20%），需实测校准
- **固定开销假设**: $\alpha_G$, $\alpha_C$ 假设为常数，实际可能随 pool_size 和场景变化
- **稳态假设**: 仅覆盖 refill 阶段，drain 阶段（< 3%）未分析
- **场景依赖**: $\rho$ 的数值基于 porous 场景；其他场景（纯辐射、纯导热）的 $\rho$ 需要独立测量
