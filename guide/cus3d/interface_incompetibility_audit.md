# 类型不匹配审计流程

## 概述

将[star3d项目](../../stardis-cpu/star-3d/0.10/)（以下简称`s3d`）的后端从Embree迁移到cuBQL是一个复杂的过程，需要对`s3d`项目对外接口和结构体所依赖的Embree进行审计。

## 背景和要求

迁移要求

- 首先将项目的CMakeLists.txt中Embree依赖完全移除，并将所有`.c`源文件替换为`.cpp`源文件以支持C++编译。
- 后端依赖Embree从环境中完全拆离时，可分析类型不匹配（即来自Embree的类型丢失，所有支持丢失的地方最后要被CuBQL替代）。
- 基于详细的类型不匹配审计报告，可以首先实现接口和结构迁移到CuBQL，然后再实现具体的后端逻辑迁移。
  
本文为审计流程指南，重点包括：

- 本文讨论迁移过程中的接口和结构体类型不匹配审计流程的背景和方法。
- 本文假设已经完成了构建系统配置和文件后缀名更改的迁移准备工作。
  
本文不包括且不得做出与下列项目相关的操作：

- 本文不讨论具体的迁移实现细节。
- 本文不讨论项目构建迁移。
- 不得直接修改代码。
- 不得直接实现迁移。

## 审计范围

- 审计范围仅限于`s3d`项目中的头文件（`*.h`）中的函数和结构体，不包括源文件（`*.c`或`*.cpp`）。

## 审计产出

- 审计报告，审计报告名为`interface_incompetibility.md`，内容包括：
  - 审计项目的文件组织结构，包括完整的目录结构和每个文件的作用。
  - 按文件组织的接口和结构体类型不匹配详情，包含：
    - 缺失信息（未定义或不允许使用不完整的定义）的具体类型、函数、宏名称。
    - 错误发生所在的结构体名称、接口名称
    - 定义缺失对象或类型在使用处和在`s3d`中的作用
    - 定义缺失类型在EmbreeWiki中的作用描述。
    - CuBQL Wiki中反查起到相同作用或扮演相同角色的类型、函数、宏名称（如果存在），若不存在，还需注明该用途在CuBQL应该通过何种方式实现。

## 参考

可以利用LSP或IDE，通过类型信息错误，在所有`*.h`头文件中审查接口和结构体对Embree类型和API的依赖情况，此时，结合`*.c`文件具体实现中的这些类型的使用点和[Embree Deepwiki](https://deepwiki.com/RenderKit/embree)，可以明确这些接口和结构体是如何依赖Embree的。
通过接口和结构体的作用，在[CuBQL Deepwiki](https://deepwiki.com/nvidia/cubql)中可反查是否存在相应的结构。
