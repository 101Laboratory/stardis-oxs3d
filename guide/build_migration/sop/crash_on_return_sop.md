# 面向 LLM 的「退出阶段崩溃」排查 SOP（可恢复 / 最小侵入）

## 适用范围
- 平台 / 构建系统迁移期  
- 程序 **main 正常结束，但在 exit / CRT 阶段崩溃**  
- 老平台 / 老构建系统 **无法作为可运行基线**  

---

## 核心原则（给 LLM 的约束）

- 不重构
- 不改业务逻辑
- 不修“看起来像 bug 的地方”
- 每一步只改变一个变量
- 任一步失败可立即回滚
- 所有操作应 **可恢复、可复现**

---

## SOP-0：环境记录（只读）

> 不允许修改代码

记录以下信息：

- OS / 架构  
- 编译器 + 版本  
- 构建系统  
- Debug / Release  
- CRT / libc 类型  
- 是否存在 DLL / so  

---

## SOP-1：退出阶段快速验证（零侵入）

**目的**：判断是否为 exit / 析构 / CRT 问题

### 操作（可回滚）

将原 `main` 的退出方式替换为：

```c
int main() {
    // 原代码
    _exit(0);   // Windows: _exit
}
```

### 判定

| return 0 | _exit(0) | 结论 |
|---------|----------|------|
| 崩 | 不崩 | 退出阶段 / 析构 / CRT |
| 崩 | 崩 | 非 exit 问题 |
| 不崩 | 不崩 | 问题消失（记录） |

> 完成后 **立即回滚**

---

## SOP-2：人工基线（最小可执行）

**目的**：验证新平台 + 新构建系统本身是否安全

### 操作

新增独立 target / project（不改原工程）：

```c
int main() {
    return 0;
}
```

- 使用 **同一构建系统 / 编译选项**

### 判定

- 崩 → 构建系统 / CRT / 入口点问题  
- 不崩 → 原工程代码引入了问题  

> 保留该人工基线，后续复用

---

## SOP-3：模块级二分（只启停，不改逻辑）

**目的**：定位第一个污染退出阶段的模块

### 方式（任选其一）

- 构建选项开关  
- link / unlink 模块  
- `#ifdef DISABLE_MODULE_X`

### 流程示例

```plaintext
人工基线 → OK
+ 模块 A → OK
+ 模块 B → OK
+ 模块 C → exit 崩
```

> 记录 **第一个引入即 exit 崩的模块**

---

## SOP-4：析构路径观测（只加日志）

**原则**：只观测，不改行为

### 允许的位置

- main 返回前  
- `atexit` 回调  
- 全局 / static 析构  
- 模块 shutdown（如存在）

### 目标

- 确认最后一个“安全执行点”
- 判断是否进入析构 / CRT 清理路径

---

## SOP-5：构建一致性快检（只读）

> 不改代码，只检查产物

逐模块确认：

- 编译器是否一致  
- CRT 是否一致（如 `/MD` vs `/MT`）  
- Debug / Release 是否混用  
- EXE / DLL 是否混 CRT  

---

## SOP-6：最小止血验证（临时，可回滚）

**目的**：验证结论，不作为最终修复

### 允许的操作（任选）

- 临时禁用问题模块析构  
- main 中显式调用模块 shutdown  
- 使用 `_exit` 作为绕过验证  

> 验证完成后回滚

---

## SOP-7：输出给 LLM 的最小结论格式

> 不贴大段代码，不提前猜原因

推荐输出：

- exit 阶段是否崩溃：是 / 否  
- `_exit` 是否可绕过：是 / 否  
- 第一个引入即崩的模块  
- 是否涉及 DLL / CRT  
- 是否涉及全局 / static 析构  

---

## 一句话结论模板（可直接喂给 LLM）

> 这是一次平台迁移引入的退出阶段问题。  
> 通过 `_exit`、人工基线和模块二分，  
> 已定位到第一个污染 exit 的模块，  
> 问题发生在析构 / CRT 清理路径。
