# oxstar-3d 光追查询服务潜力评估

**日期**: 2026-03-01  
**数据来源**: `perf_diag/optix_throughput_results.csv`, `perf_diag/s3d_embree_throughput_results.csv`, `perf_diag/log.txt`  
**GPU 测试平台**: NVIDIA GeForce RTX 4090 (SM 8.9, 24GB, 128 SMs, 128 RT Cores)  
**CPU 测试平台**: Intel Core i9-13900K (8P+16E, 24T, L3=36MB, DDR5-5600)  
**GPU 对比平台**: NVIDIA GeForce RTX 3070 Laptop (SM 8.6, 8GB, 40 SMs, 40 RT Cores)

**管线架构**: Unified Pipeline (单 Pipeline, 三 SBT: RT + MH + NN)

## 1. 核心结论

oxstar-3d 的 OptiX 统一管线在 RTX 4090 上展现出**极强的光追查询服务潜力**：

| 能力维度 | RTX 4090 实测值 | 求解器需求 | 余量 |
|----------|-----------------|------------|------|
| 峰值吞吐 (简单场景) | 10.79 GRays/s | — | 基线 |
| 峰值吞吐 (10K 三角形) | 5.32 GRays/s (kernel) | — | 基线 |
| 持续吞吐 (10s) | 5.28 GRays/s | — | 无 throttling |
| 单批延迟 @8M rays | 1.63 ms (p50) | <10 ms | 6x |
| 单批延迟 @2M rays | 0.42 ms (p50) | <10 ms | 24x |
| 双流重叠比 | 1.98x (256 批次) | — | 接近理论 2x |
| BVH 构建 (10K 三角形) | 1.14 ms | <100 ms | 88x |
| 最近点查询 (100K 三角形) | 11.81 MQuery/s | — | 稳定 |

**核心发现: 10 秒压力测试中 4090 温度未超过 50°C，意味着 GPU 功耗仅约 80-90W (TDP 450W 的 ~18%)。当前测试仅激活了 RT Core，SM 和 Tensor Core 几乎全部空闲。oxstar-3d 光追服务远未触及 4090 的硬件极限。**

## 5. 持续稳定性与热特性

**稳定性结论:**
- 稳态吞吐: **5,283 MRays/s (5.28 GRays/s)**, 10 秒零衰减
- p50 漂移: 3.155 → 3.159ms (仅 +0.13%)

### 5.2 温度不变的根因

10K 三角形的 RT 追踪仅激活了 4090 硬件的一小部分:

| 芯片组件 | 峰值功耗 | 本测试状态 | 估算功耗 |
|----------|----------|-----------|----------|
| CUDA Cores (16384) | ~250W | 几乎空闲 (仅 hit/miss 写入) | ~10W |
| RT Cores (128) | ~40W | 间歇活跃 (BVH 遍历) | ~20-30W |
| Tensor Cores (512) | ~100W | 完全空闲 | 0W |
| L2 Cache (72MB) | — | 低压力 (10K BVH 全部放入) | ~5W |
| 显存子系统 (21Gbps) | ~50W | 低带宽利用 | ~15W |
| 基础/固定功耗 | ~35W | 恒定 | ~35W |
| **合计** | **450W TDP** | | **~85-95W (~20%)** |

这意味着 **GPU 有 80% 的计算余量可供上层求解器使用** — 例如 CUDA Kernel 计算 Green 函数、温度场更新、蒙特卡洛采样权重等。

## 6. 对 Stardis 求解器的服务能力映射

### 6.1 查询延迟预算分解

Stardis 求解器每次 Picard 迭代的热路径:

```
[CPU 状态机] → [GPU RT 查询] → [CPU 结果处理] → [GPU RT 查询] → ...
              ↑                                  ↑
           单次 traceBatch                    单次 traceBatch
```

基于 Realistic A 数据 (`real_a_width`)，不同 pool_size 的单次查询延迟:

| pool_size | T_kernel (ms) | T_total (ms) | 瓶颈 |
|-----------|---------------|--------------|------|
| 32K (当前目标) | 0.044 | 0.069 | **CPU 提交 (64μs > kernel 44μs)** |
| 262K | 0.085 | 0.089 | kernel 开始主导 |
| 1M | 0.221 | 0.224 | kernel 主导 |
| 8M (W_sat) | 1.630 | 1.665 | kernel 主导, GPU 饱和 |

> CSV 引用: `real_a_width,32768,64.4,24.672,0.043936,0.068608,745.812,477.612,0.745812,0.0785217`  
> CSV 引用: `real_a_width,1048576,19.5,4.832,0.221184,0.22384,4740.74,4684.49,4.74074,0.0778093`

### 6.2 pool_size 甜蜜点分析

结合 B2 间隔敏感度数据，求解器 CPU 状态机处理时间约 50-500μs:

| CPU 处理时间 | 推荐 pool_size | GPU 利用率 | 有效吞吐 |
|-------------|----------------|-----------|----------|
| 50 μs | ≥262K | 79.4% | 3.2 GRays/s |
| 100 μs | ≥1M | 71.8% | 2.9 GRays/s |
| 500 μs | ≥4M | 33.9% | 1.4 GRays/s |

**建议: 将 pool_size 从 32K 提升至 256K-1M** 以平衡 CPU 状态机处理能力与 GPU 利用率。在 4090 上，32K batch 的 kernel 仅 44μs，而 CPU 提交就要 64μs，GPU 几乎在空转。

### 6.3 求解器期望吞吐

假设 Stardis 每条蒙特卡洛路径平均产生 5-10 次 RT 查询:

| 场景 | 路径数/批 | RT查询/批 | 单批时间 | 批次率 | 路径吞吐 |
|------|----------|----------|----------|--------|----------|
| 保守 (pool=32K) | 32K | 160K-320K | 0.07ms | 14,285/s | 457M 路径/s |
| 推荐 (pool=256K) | 256K | 1.3M-2.6M | 0.5ms | 2,000/s | 512M 路径/s |
| 激进 (pool=2M) | 2M | 10M-20M | 4ms | 250/s | 500M 路径/s |

实际吞吐瓶颈在 CPU 状态机而非 GPU，因此推荐方案从 **总路径吞吐** 角度与激进方案差距不大，但 CPU 端压力更均衡。

## 7. 与 custar-3d (cuBQL) 的对比定位

| 维度 | custar-3d (cuBQL) | oxstar-3d (OptiX) |
|------|--------------------|--------------------|
| BVH 构建 | 软件 BVH, 可定制 | 硬件 BVH (RT Core), OptiX 自动优化 |
| RT 追踪 | CUDA Kernel 遍历 | RT Core 硬件遍历 |
| 最近点查询 | 自定义 BVH 搜索 | optixTrace closest-hit 模拟 |
| 峰值 RT 吞吐 | ~2 GRays/s (估算) | **10.8 GRays/s (实测)** |
| 峰值 CP 吞吐 | 未测 | **11.8 MQuery/s (实测)** |
| SM 利用率 | 高 (BVH 遍历占用 SM) | 低 (RT Core 专用硬件, SM 空闲) |
| 扩展性 | SM-bound | **RT Core-bound, SM 可做额外计算** |

**oxstar-3d 的关键优势: RT 追踪卸载到专用 RT Core，释放 SM 给上层求解器用于并行计算。** 这使得光追和温度场更新可以真正并行，是 cuBQL 无法实现的架构级优势。

## 9. CPU 对比基线: star-3d (Embree 4) 后端

### 9.1 架构概述

star-3d 是 Stardis 的 **原始 CPU 光追后端**，基于 Intel Embree 4，提供与 oxstar-3d / custar-3d **完全相同的 `s3d.h` 公共 API**（~70 个函数）。其关键架构特征：

| 维度 | star-3d (Embree 4) | oxstar-3d (OptiX 9.1) |
|------|--------------------|-----------------------|
| 计算设备 | CPU | GPU (RT Core) |
| BVH 实现 | Embree 软件 BVH (SIMD 优化) | OptiX 硬件 BVH (RT Core) |
| 单次追踪 | `rtcIntersect1` (标量) | `optixTrace` (kernel) |
| 批量追踪 | **串行循环** (`trace_rays` = N × `trace_ray`) | GPU 批量 launch (`traceBatch`) |
| 最近点查询 | `rtcPointQuery` | `optixTrace` closest-hit 模拟 |
| SIMD 数据包 | 未使用 (`rtcIntersect4/8/16` 可用但未集成) | N/A (硬件隐式并行) |
| 线程安全 | `RTCScene` commit 后可多线程并发读 | CUDA Stream 并发 |
| 内部线程池 | **无** — 需上层管理线程 | OptiX 自动调度 SM |
| BVH 质量选项 | LOW / MEDIUM / HIGH + ROBUST / DYNAMIC / COMPACT | OptiX 自动优化 |
| 内存模型 | CPU 堆, 手动管理 (rsys allocator) | GPU VRAM (CUdeviceptr) |

### 9.2 关键实现细节

**`s3d_scene_view_trace_ray` (单射线)**
- 位置: `stardis-cpu/star-3d/0.10/src/s3d_scene_view_trace_ray.c:138`
- 调用链: 参数校验 → `RTCRayHit` 初始化 → `rtcIntersect1(rtc_scn, &ray_hit, &intersect_args)` → `hit_setup` 后处理
- 关键开销: Embree `rtcIntersect1` 是纯 CPU SIMD 遍历，单射线延迟取决于 BVH 深度和缓存命中率

**`s3d_scene_view_trace_rays` (批量射线)**
- 位置: `stardis-cpu/star-3d/0.10/src/s3d_scene_view_trace_ray.c:219`
- **实现: 纯串行 `FOR_EACH` 循环逐条调用 `s3d_scene_view_trace_ray`**
- 未使用 Embree 4 的 SIMD 数据包接口 (`rtcIntersect4/8/16`)，也未使用流式接口 (`rtcIntersectN`)
- 这意味着**批量 API 无额外优化增益**，仅是语法糖

**`s3d_scene_view_closest_point` (最近点)**
- 位置: `stardis-cpu/star-3d/0.10/src/s3d_scene_view_closest_point.c`
- 调用 `rtcPointQuery`，搜索半径由 `radius` 参数指定
- 内含双精度三角形最近点计算 (`closest_point_triangle`)

**线程模型**
- `s3d_device` 持有一个 `RTCDevice`，仅初始化时指定 `verbose` 选项
- Embree 4 保证: `rtcCommitScene` 完成后，**任意数量线程可并发调用 `rtcIntersect1`**
- star-3d 自身**不创建或管理任何线程** — 完全依赖上层求解器 (stardis-solver) 的线程调度
- 实际部署中，stardis-solver 使用操作系统线程手动并发，每线程独立调用 `trace_ray`

### 9.4 与 oxstar-3d 实测对比

**场景对齐**: 两个后端使用相同 PCG hash RNG 生成随机三角形场景, 相同种子 (seed=77/42), 命中率一致 (GPU 8.5%, CPU 8.3%)。

#### 核心指标对比

| 测试条件 | oxstar-3d (RTX 4090) | star-3d (i9-13900K) | GPU/CPU 比 |
|----------|---------------------|---------------------|-----------|
| RT @10K, 1M rays, 1T | 4,633 MRays/s | 0.83 MRays/s | **5,580x** |
| RT @10K, 全力峰值 | 5,146 MRays/s¹ | 15.45 MRays/s (16T) | **333x** |
| RT 持续 10s | 5,283 MRays/s | 6.61 MRays/s (8T) | **799x** |
| CP @10K, 1T | 15.60 MQuery/s | 0.79 MQuery/s | **19.7x** |
| CP @100K, 1T | 11.72 MQuery/s | 0.52 MQuery/s | **22.5x** |
| CP @1M, 1T | 8.73 MQuery/s | 0.19 MQuery/s | **45.9x** |
| BVH 构建 @10K | 1.14 ms | 2.19 ms | **1.9x** |
| BVH 构建 @1M | 24.0 ms | 31.8 ms | **1.3x** |

¹ GPU 取 `real_a_width,8388608` kernel 值 = 5,146 MRays/s

#### 复杂度-吞吐交叉分析 (Test D vs complexity, 1M rays)

| 三角形数 | GPU RT | CPU RT | GPU/CPU | GPU CP | CPU CP | GPU/CPU |
|----------|--------|--------|---------|--------|--------|---------|
| 1 | 10,449 | 2.31 | 4,524x | 2,032 | 10.81 | 188x |
| 1,000 | 11,406 | 1.43 | 7,976x | 19.65 | 1.19 | 16.5x |
| 10,000 | 4,633 | 0.83 | 5,580x | 15.60 | 0.79 | 19.7x |
| 100,000 | 1,204 | 0.48 | 2,508x | 11.72 | 0.52 | 22.5x |
| 1,000,000 | 1,250 | 0.44 | 2,841x | 8.73 | 0.19 | 45.9x |

> 单位: MRays/s (RT), MQuery/s (CP)

#### 关键发现

**1. RT 对比: 量级差异 (333x — 5,580x)**

- RT Core 硬件加速赋予 GPU 3+ 个数量级的吞吐优势。即使 CPU 用满 16 线程 (全 P-core + 部分 E-core), 差距仍达 **333x**
- GPU 和 CPU 随复杂度变化的趋势**不同**: GPU 在 10K→100K 三角形区间急剧下降 (4,633→1,204, −74%), CPU 下降更平缓 (0.83→0.48, −42%)。超大场景下比率收窄至 ~2,500x
- **L3 悬崖 vs GPU 管线填充**: CPU 核心瓶颈是 L3 溢出 (262K→4M rays 导致 2.4x 衰减); GPU 在同等射线数范围内仍处于管线填充阶段 (吞吐持续上升直到 ~8M rays 饱和)

**2. CP 对比: 中等差异 (16x — 46x)**

- CP 比率远低于 RT, 因为 OptiX 无原生最近点查询硬件 (通过 closest-hit 模拟)
- 1M 三角形时比率飙升至 **46x** — CPU `rtcPointQuery` 的双精度回调在大 BVH 下严重恶化 (0.79→0.19, −76%), GPU 仅下降 44% (15.6→8.7)
- 求解器典型场景 (10K-100K 三角形), CP 比率稳定在 **~20x**

**3. BVH 构建: 微弱差异 (1.3x — 1.9x)**

- BVH 构建是 CPU 唯一接近 GPU 的领域。Embree 多线程 BVH 构建成熟度极高
- 动态场景需频繁重建 BVH 时, 此差距可忽略

**4. 资源利用完全不对称**

- **oxstar-3d**: RT 追踪由 RT Core 执行, SM 空闲率 ~80%, 温度 <50°C (功耗 ~85W / TDP 450W 的 18%)
- **star-3d**: BVH 遍历消耗 CPU 全部计算资源 (16T 满载), 与求解器计算直接争抢。24T 时 E-core 回归导致效率崩塌至 61%

**5. 对求解器并行化的启示**

- GPU `pool_size` 甜蜜点 (8,192 paths @8M rays/batch @1.63ms) 可在 RT Core 处理光追的同时释放 SM 给求解器计算内核
- CPU 无此分离: 增大 pool_size 会加剧 L3 压力 → RT 吞吐从 2.04 崩塌至 0.84 MRays/s。 CPU pool_size 上限受 L3 缓存约束 (~262K rays/batch)
- 先前§9.3估算 (RT ~100-200 MRays/s, CP ~5-20 MQuery/s) 严重高估 — star-3d 仅使用 `rtcIntersect1` 标量接口, 实际比 Embree 官方基准 (使用 `rtcIntersect8/16` 数据包) 低约 **50-100 倍**
